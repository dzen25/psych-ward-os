# Psych Ward OS — тестовые хуки `/sbin/tests`

Вынесено из [COMMANDS.md](COMMANDS.md) 2026-09-06: раздел разросся до
состояния, когда таблица перестала читаться. Здесь — только тесты, там —
только команды шелла.

Каждый тест — постоянный регрессионный стенд под конкретный пункт
`issuse.txt`, а не одноразовый скрипт: закрытый баг остаётся закрытым
ровно до тех пор, пока его тест продолжает проходить.

Собираются с префиксом `sbtest_` (не `sb_`, см. `build_and_sign.sh`) и
лежат в отдельной папке — чтобы не путались с `/sbin` при `ls`.
Список целей — `PSYCH_TEST_TOOLS` в `CMakeLists.txt`; новый тест
достаточно добавить туда, раскладка и подпись подхватятся сами.

Запускать полным путём:

```
exec /sbin/tests/<имя>.elf [аргументы]
```

Формат вывода общий: `ТЕСТ N: ...` / `ТЕСТ N ЗАВЕРШЁН`, при провале —
`ТЕСТ N ОСТАНОВЛЕН — ОШИБКА: <причина>` с прекращением прогона.

<details>
<summary><b>🔁 <code>stresstest</code> — N спавнов подряд — нагрузка на сам <code>spawn_process()</code> и аллокацию CNode/VSpace/TCB</b></summary>

**Аргументы:** `[итераций]`

спавнит `/bin/test_app.elf` N раз подряд (по умолч. 30) сырыми SYS_EXEC/SYS_WAIT, печатая номер итерации перед каждым спавном — воспроизводимая, без участия человека, стресс-нагрузка на сам `spawn_process()`/CNode-VSpace-TCB-аллокацию для issuse.txt №62 (спорадические крахи/зависания при старте процесса). До 2026-08-23 гоняла ротацию из 7 `/sbin`-команд (ls/ps/free/touch/cat/mkdir/rm) — после их слияния в `shell.cpp` спавнить их по пути через `SYS_EXEC` уже нельзя, разнообразие проверяемых путей (exFAT-запись/чтение через разные процессы подряд) этим прогоном больше не покрывается. Также регрессия для issuse.txt №65 (командная RAM-арена снова включена, но только под ELF/стек/IPC-страницы, см. `force_pool` у `ram_retype()` в main.cpp) — 300 итераций hw-подтверждены 2026-08-24: 0 крашей/зависаний, `free`/Used вырос всего на ~10МиБ (только неизбежный CNode/VSpace/TCB-оверхед из общего пула, было бы ~50МиБ+ с полностью выключенной ареной)

<details>
<summary><b>⏱️ <code>timedread</code> — чтение файла чанками с прогрессом и таймингом; штатный репро для watchdog/VFS-мьютекса</b></summary>

**Аргументы:** `<файл> [интервал прогресса в чанках, по умолч. 32]`

читает файл целиком чанками SYS_READ_FILE (тот же путь, что теперь и `cat`), печатая прогресс (по умолч. каждые 32 чанка = ~128КБ) и итоговое время в мс — не печатает содержимое; исходно для проверки 3-секундного бюджета heartbeat-watchdog'а blk_driver (issuse.txt №63a). Второй аргумент (issuse.txt №69, найдено при ручном тесте) — 128КБ-интервал заливает консоль настолько, что не остаётся окна набрать `kill <pid>` руками в тот же терминал; большой интервал (например `timedread bigfile.txt 2000`) даёт паузу в несколько секунд между строками. Также регрессия для issuse.txt №66 (watchdog путал "занят долгой VFS-операцией" с "завис", убивал живой driver и НАВСЕГДА вешал синхронно ждавшего клиента) — hw-подтверждено 2026-08-24: `blk_driver`/`hardware_emmc_read/write()` теперь сигналят liveness на каждом реальном сектор-I/O, не только по простою; 124МиБ файл, 30304 чанка, ни одного ложного убийства. Тот же фикс симметрично применён к `usb_driver.cpp` (`hardware_usb_rw_generic_read/write()`), но ещё не hw-подтверждён. Также стандартный репро-инструмент для issuse.txt №70 (ЗАКРЫТ, hw-подтверждено 2026-08-24) — `kill <pid timedread>` во время фонового прогона (держит `vfs_lock()` весь прогон) раньше НАВСЕГДА вешал вообще любую VFS-команду от любого процесса (глобальный `vfs_mutex_ep` не переживал смерть держателя); фикс — `vfs_lock()`/`vfs_unlock()` сами сообщают root'у о владении (`SYS_VFS_LOCK_NOTIFY`), `generic_recover_process()` форсирует освобождение при смерти держателя

</details>

<details>
<summary><b>💥 <code>killwindow</code> — <code>kill</code> драйвера ровно посреди обработки VFS-команды</b></summary>

**Аргументы:** —

детерминированный тест для issuse.txt №69 (ЗАКРЫТ, hw-подтверждено 2026-08-24) — шлёт ОДИН SYS_READ_FILE с сентинел-offset'ом (`KILL_WINDOW_TEST_OFFSET`, common.h) напрямую в `blk_ep`, БЕЗ `vfs_lock()`; blk_driver.cpp узнаёт сентинел и делает искусственную 5-секундную паузу ПОСЛЕ SaveCaller — гарантированное окно, чтобы во время паузы вручную выполнить `kill <pid blk_driver>` РОВНО посреди обработки VFS-команды. status=-1 при быстром ответе = сработал rescue-механизм root'а (`generic_recover_process()`/`VFS_PENDING_REPLY_SLOT`) — именно это и подтвердилось (`status=-1`, t=2526мс, лог "Найден зависший VFS-клиент"). Первая попытка использовала `seL4_CNode_Copy` — hw упало с "Mutated cap would be invalid" (reply-капы в seL4 принципиально некопируемы, только `seL4_CNode_Move`); тест только для blk_driver — usb_driver'овская сторона того же механизма (issuse.txt №69, симметричный SaveCaller в usb_driver.cpp) остаётся не hw-подтверждённой

<details>
<summary><b>🧠 <code>coretest</code> — сводный автотест переноса драйверов между ядрами и сброса USB, 10 шагов</b></summary>

**Аргументы:** `[номер шага] [путь к большому файлу]`

сводный автотест адаптивного переноса драйверов между ядрами (issuse.txt №74/б) и полного сброса USB (№74/в). 10 шагов, каждый печатает `ТЕСТ N: ...` / `ТЕСТ N ЗАВЕРШЁН`; при провале — `ТЕСТ N ОСТАНОВЛЕН — ОШИБКА: <причина>` и прогон прекращается. Без аргументов гоняет все шаги на `/root/bigfile.txt`; `coretest 7` — только седьмой шаг; `coretest 0 /root/other.txt` — все шаги на другом файле. Ключевой шаг 7 делает то, что человек за одним терминалом выполнить не может: длинное чтение файла уходит в отдельный поток (`SYS_CLONE`), а главный поток в это же время в цикле дёргает `balance` — успех означает, что файл дочитан целиком и его контрольная сумма совпала с эталонным прогоном без балансировки. Содержимое файла НЕ печатается (он большой) — сравниваются длина и контрольная сумма. Шаг 8 — бывший детерминированный дедлок: `recover` драйвера, живущего на не-нулевом ядре (раньше root навсегда уходил в `ipi_wait()`). Шаги 9/10 (wifi stop/start, `usbreset`) пропускаются, если соответствующий драйвер не запущен. Понадобились два небольших дополнения в root: `SYS_PROC_INFO` (pid/ядро/состояние PARKED-BUSY по имени — разбор человекочитаемого `ps` для теста слишком хрупок) и «тихий» режим `SYS_BALANCE` (MR1=1, не пишет отчёт в общую SHM-страницу — иначе затирал бы данные файла, которые в этот момент читает поток)

</details>

<details>
<summary><b>🔌 <code>hotplugtest</code> — многократное горячее переподключение USB-накопителя</b></summary>

**Аргументы:** `[циклов] [мс_снятого_питания]`

устойчивость монтирования USB к многократному горячему переподключению. Дёргает питание downstream-порта хаба (`PORT_POWER`) — для устройства это электрически то же, что вынуть и вставить флешку, — и после каждого цикла проверяет, что том вернулся И отвечает на запрос ФС (голого бита «смонтировано» мало: он мог пережить прошлую инкарнацию слота). Печатает `ЦИКЛ N/M ЗАВЕРШЁН — том вернулся за Xмс` либо `ЦИКЛ N ОСТАНОВЛЕН — ОШИБКА: ...` и прекращает прогон на первом отказе. По умолчанию 20 циклов, питание снято 800мс. Заменяет ручной ритуал «выньте-вставьте флешку 10 раз», который занимал минуты и давал невоспроизводимый результат. Требует, чтобы накопитель был воткнут В ХАБ (за корневым портом цикл питания делать нечем)

</details>

<details>
<summary><b>🐕 <code>stalltest</code> — проверка САМОГО watchdog'а — драйвер имитирует зависание</b></summary>

**Аргументы:** `[мс_зависания]`

стенд для проверки САМОГО watchdog'а — та самая «часть а» плана, до которой раньше не доходили руки. Драйвер по команде объявляет шаг и крутится заданное время, **не** трогая счётчик прогресса и не возвращаясь в `seL4_Recv`: для root'а это неотличимо от ядра, замершего на аппаратной транзакции. Проверяется ровно тот детектор, который должен ловить реальный отказ. По умолчанию 15с при пороге срабатывания 10с. Успех = в логе есть `[WATCHDOG] ... прогресс замер на шаге ...`, сброс шины выполнен, **и плата осталась жива** (тест досчитывает до конца и печатает итог). Требует `usb_driver` в `/etc/auto_restart.conf` — иначе автотриггер выключен и сторож промолчит

</details>

<details>
<summary><b>🌀 <code>spawnloop</code> — спавн одной команды N раз — ловля падения при старте процесса</b></summary>

**Аргументы:** `[итераций] [команда]`

воспроизводитель плавающего падения тестового процесса (issuse.txt №3): спавнит указанную команду N раз через сырые `SYS_EXEC`/`SYS_WAIT`, печатая номер итерации ПЕРЕД каждым спавном — в логе видно, на какой именно случился `FATAL FAULT`. По умолчанию 30 итераций короткого `hotplugtest.elf 1 300`. Сам про падение ребёнка не узнаёт (`SYS_WAIT` возвращается одинаково и после нормального выхода, и после восстановления — та же особенность, что у `stresstest`), признак ищется в логе rootserver'а. Контрольный опыт для разделения гипотез: `spawnloop 100 /bin/test_app.elf` — если с обычным бинарником не падает, дело не в спавне/PID/арене как таковых **ЗАКРЫТО 2026-09-06:** отказ оказался устаревшим кэшем ИНСТРУКЦИЙ — `spawn_process()` чистил кэш ДАННЫХ (`Page_Clean_Data`) для страниц, в которые записан КОД, а все `/sbin`-бинарники слинкованы на один адрес `0x400000`, поэтому новый процесс исполнял код предыдущего. Фикс — `Page_Unify_Instruction`. Именно этот контрольный опыт и вводил в заблуждение: 100 спавнов ОДНОГО бинарника проходят чисто, потому что устаревшие строки I-кэша совпадают с нужными; ломается только связка ДВУХ РАЗНЫХ утилит подряд. Рабочий репро: `hotplugtest 150 300`, затем `spawnloop 150`

</details>

<details>
<summary><b>👻 <code>orphantest</code> — уборка SYS_CLONE-потоков за завершившимся процессом</b></summary>

**Аргументы:** `[циклов]`

уборка `SYS_CLONE`-потоков за завершившимся процессом (issuse.txt №3, побочная находка). Спавнит сам себя в служебном режиме `leak` (создаёт поток и выходит, НЕ дожидаясь его), затем проверяет, что root его добрал. Детектор не потребовал нового syscall'а: все клон-потоки называются `shell_thread`, а `SYS_PROC_INFO` возвращает первый АКТИВНЫЙ PCB с таким именем — значит `-1` = чисто, `>=0` = утечка с номером PID. Шаг 6 повторяет цикл N раз (по умолч. 10), проверяя заодно, что не растут PID/слоты CNode и что VFS отвечает. До фикса каждый такой выход оставлял PCB навсегда `active`, исполняющийся поток БЕЗ адресного пространства и захваченный навсегда глобальный `vfs_mutex_ep`. Запускать с чистого старта — шаг 1 отказывается работать, если висящий поток уже есть

</details>

<details>
<summary><b>📝 <code>logtest</code> — накопитель в режиме журнала/бортового самописца — тысячи мелких записей</b></summary>

**Аргументы:** `<путь> [итераций] [байт] [rewrite\|append] [same\|random] [stream\|nostream] [keep\|delete]`

накопитель в режиме журнала/бортового самописца: тысячи мелких записей в один файл с посверкой. Порядок аргументов после пути произвольный; из чисел первое — итерации (по умолч. 1500), второе — байт за итерацию (по умолч. 256, потолок 4096 — одна staging-страница SHM драйвера, см. `BLK_SHM_STAGING_OFFSET`). Путь — каталог тома (файл будет `<путь>/logtest.log`) либо сразу имя файла, если в последнем сегменте есть точка. Три независимые оси: `rewrite` перезаписывает файл целиком (размер постоянный, износ одного места) против `append` (файл растёт); `same` пишет одну и ту же узнаваемую строку против `random` (своё содержимое на итерацию); `nostream` сверяет чтением после каждой записи (задержка подтверждённой записи) против `stream` (сверка одна, в конце — пропускная способность). `delete` убирает файл после прогона и проверяет, что он действительно перестал читаться. **Важно для трактовки:** при `same` сверка не отличит новую запись от прошлой — содержимое одинаковое; связка «`same` прошёл И `random` прошёл» сильнее любого по отдельности. Вместе с этим тестом в систему добавлен НАСТОЯЩИЙ append (`exfat_append_file()`, cmd 121 в blk/usb_driver) — до 2026-09-06 единственной записью была перезаписывающая файл целиком



**Аргументы.** Порядок после пути произвольный: слова распознаются по значению, числа — по позиции.

| Аргумент | Значения | По умолч. | Что делает |
|---|---|---|---|
| путь | каталог тома или файл | обязателен | каталог → файл будет `<путь>/logtest.log`; если в последнем сегменте есть точка, берётся как имя файла |
| 1-е число | итерации | `1500` | сколько записей сделать |
| 2-е число | байт за итерацию | `256` | размер одной записи; потолок — `VFS_PAYLOAD_MAX` (см. platform.h) |
| — | `rewrite` | по умолч. | каждая итерация перезаписывает файл ЦЕЛИКОМ; размер постоянный, износ одного места носителя |
| — | `append` | | каждая итерация ДОПИСЫВАЕТ в конец, файл растёт |
| — | `direct` | | потоковая запись: место резервируется при открытии, метаданные обновляются один раз при закрытии. Включает `append` и `stream` автоматически |
| — | `same` | по умолч. | одна и та же узнаваемая строка (`PSYCH-WARD-OS LOGTEST RECORD…`) |
| — | `random` | | своё псевдослучайное содержимое на каждой итерации (зерно фиксировано, эталон пересчитывается) |
| — | `nostream` | по умолч. | сверка чтением ПОСЛЕ КАЖДОЙ записи — меряет задержку подтверждённой записи |
| — | `stream` | | без посверки, сверка одна в конце — меряет пропускную способность |
| — | `keep` | по умолч. | файл остаётся на носителе |
| — | `delete` | | файл удаляется после прогона, и проверяется, что он действительно перестал читаться; уборка срабатывает и при аварийном выходе |

**Три оси независимы:** что делаем с файлом (`rewrite`/`append`/`direct`), что пишем (`same`/`random`), как меряем (`nostream`/`stream`).

**Важно для трактовки результата:** при `same` сверка чтением не отличит новую запись от прошлой — содержимое одинаковое. Поэтому `same` проверяет живучесть пути записи и износ носителя, а `random` — ещё и что данные реально доехали. Связка «оба прошли» сильнее любого по отдельности.

**Шаги:** 1 — файл создан и обнулён; 2 — основной цикл; 3 — весь файл перечитан по смещениям и совпал; 4 — файл удалён (только при `delete`).

**Что печатает по итогам:** разбивку SCSI по фазам (CBW / данные / CSW), раздельно скорость чтения и записи, счётчики блочных операций по вызывающему (поиск в битмапе, обход каталога, запись потока…) и прямые счётчики вызовов — этим инструментом и находились узкие места.

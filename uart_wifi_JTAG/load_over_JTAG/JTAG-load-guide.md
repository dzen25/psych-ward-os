# Загрузка образа в ОЗУ через JTAG

Цель: во время разработки не переписывать SD-карту после каждой правки, а
класть свежий образ прямо в ОЗУ платы через JTAG и запускать его. Цикл
«собрал → увидел на железе» сокращается до одного скрипта с сборочного
сервера; карта из петли уходит совсем.

Отношение к соседним папкам:
- `../debug_of_FT232H/` — **физический стек JTAG** (адаптер, провода,
  конфиг OpenOCD, SSH-туннель, VSCode/F5). Всё отсюда стоит НА НЁМ и
  ничего в нём не меняет. Если JTAG ещё не поднят — сначала туда.
- `../debug_of_RP2040/`, `../debug_of_esp32c3/` — альтернативный мост и
  беспроводной UART, к этой методичке отношения не имеют.
- Эта папка — **не новый транспорт, а новый способ применения уже
  имеющегося**: тот же FT232H на carto, те же порты 3333/4444.

> **Статус: прогнано на железе 2026-09-06.** Заливка 1 950 632 байт —
> **8.42 с (226 КиБ/с)**, весь цикл со `scp` — 10.7 с. Сверка залитого с
> оригиналом в трёх точках прошла байт-в-байт. Оставшиеся непроверенные
> места помечены **[гипотеза]** прямо по тексту.

## 1. Что даёт и чего стоит

| | Штатный путь (SD) | Через JTAG |
|---|---|---|
| Что делает пользователь | `./build_and_sign.sh` → `rt/flash.sh` на Mac → вставить карту → включить | `./build_and_sign.sh` → `jtagload.sh` |
| Физические действия с платой | вынуть/вставить карту, передёрнуть питание | никаких |

| Время | минуты + ручные операции | **10.7 с** целиком (из них 8.42 с — сама заливка 1.9 МБ, 226 КиБ/с; замерено 2026-09-06) |

## 2. Что именно грузим — проверенные факты

Всё в этом разделе проверено на реальных артефактах сборки в
`build-rpi4/`, не по памяти и не по документации seL4.

- Загрузочный образ — `build-rpi4/images/sel4test-driver-image-arm-bcm2711`,
  **1 950 632 байта**. Это НЕ ELF (`readelf` ругается на magic) — плоский
  двоичный образ.
- Его ELF-оригинал с символами — `build-rpi4/elfloader/elfloader`:
  `Type: EXEC`, `Entry point: 0x10000000`, **ровно один** сегмент
  `LOAD` с `VirtAddr = PhysAddr = 0x10000000`, `FileSiz = 0x1dc3a8`,
  `MemSiz = 0x1e80a8`.
- `0x1dc3a8 = 1 950 632` — то есть плоский образ есть в точности PT_LOAD
  этого ELF. **Проверено `cmp`**: `objcopy -O binary build-rpi4/elfloader/elfloader`
  байт-в-байт совпадает с `sel4test-driver-image-arm-bcm2711`.
  Отсюда практический вывод: `load` в GDB по ELF'у кладёт РОВНО то же
  содержимое по тому же адресу, что U-Boot копирует из FIT.
- `IMAGE_START_ADDR = 0x10000000` (`build-rpi4/CMakeCache.txt`) совпадает с
  `load`/`entry` в `tools/boot_fit/boot.its.template`.
- Символы точки входа: `_start = _text = 0x10000000`,
  `secondary_startup = 0x10000054`.
- `build-rpi4/elfloader/gen_config/elfloader/gen_config.h`:
  - `CONFIG_IMAGE_BINARY = 1` — образ плоский, и crt0 умеет **сам себя
    переместить**, если оказался не по своему адресу (`fixup_image_base`
    в `tools/seL4/elfloader-tool/src/arch-arm/64/crt0.S`). То есть
    промах по адресу загрузки не фатален.
  - `CONFIG_ELFLOADER_INCLUDE_DTB = 1` — **DTB вшит в сам образ**. Никакого
    указателя на device tree в `x0` передавать не нужно, и это главная
    причина, почему запуск с JTAG вообще получается простым.
- Сборка: `SMP=ON`, `NUM_NODES=4`, `KernelPlatform=bcm2711`, `RPI4_MEMORY=4096`.

## 3. Почему это эквивалентно штатной загрузке

Важно понимать, что мы НЕ изобретаем новый способ старта — мы повторяем
существующий, вырезав из него только SD-карту. Цепочка проверена по
исходникам U-Boot (`/home/nikita/u-boot`) и по `setup_uboot_secure_boot.sh`:

```
BOOTCOMMAND (вшит в u-boot.bin, setup_uboot_secure_boot.sh:104):
    setenv autostart yes; fatload mmc 0 0x20000000 boot.itb; bootm 0x20000000
        │
        ├─ FIT: проверка подписи sha256,rsa2048
        ├─ копирование образа ядра по load = 0x10000000
        └─ boot_os[IH_OS_U_BOOT] = do_bootm_standalone   (boot/bootm_os.c:530)
               appl = (int(*)(int, char* const[]))images->ep;   // = 0x10000000
               appl(argc, argv);                                // ОБЫЧНЫЙ ВЫЗОВ
```

Ключевое, что легко предположить неверно: **`os = "u-boot"` не идёт через
`do_bootm_linux`, а значит `cleanup_before_linux()` НЕ вызывается**
(`boot/bootm_os.c:26-38` — в `do_bootm_standalone` его просто нет). То
есть в продакшне elfloader стартует при **включённых MMU, D-cache и
I-cache U-Boot'а**, а не на «чистом» процессоре. Это не проблема:
`arm_enable_mmu` (`elfloader-tool/src/arch-arm/armv/armv8-a/64/mmu.S:41`)
первым делом делает `flush_dcache`, затем `disable_mmu sctlr_el1` и только
потом ставит свои таблицы.

**Подтверждено на железе 2026-09-06** — `halt` внутри приглашения U-Boot
напечатал ровно это:

```
bcm2711.cpu0 halted in AArch64 state due to debug-request, current mode: EL2H
MMU: enabled, D-Cache: enabled, I-Cache: enabled
```

Следствие для нас: чтобы воспроизвести штатный вход, достаточно
остановить cpu0 **внутри U-Boot**, положить те же байты по тому же адресу
и выставить `pc = 0x10000000`. Ни MMU трогать, ни кэши гасить, ни DTB
подсовывать не нужно — состояние машины уже ровно то, которого elfloader
ожидает в бою.

Ядра 1-3 в этот момент так же припаркованы прошивочным armstub'ом в
spin-table — elfloader поднимет их сам (`smp_boot()` →
`smp-spin-table.c`, адреса берёт из вшитого DTB), как и при обычной
загрузке.

## 4. Предусловие: плата должна стоять в приглашении U-Boot

Это единственное неудобное место всей схемы, и обойти его нечем.

**Почему нельзя просто прервать уже работающую ОС.** К моменту, когда
шелл отвечает, ядра 1-3 больше не в spin-table — на них исполняется seL4.
Остановить cpu0 и прыгнуть в elfloader — значит запустить bring-up на
фоне трёх ядер, которые продолжают крутить старое ядро в старом
адресном пространстве. Это гарантированный мусор, а не загрузка.
Дополнительно: остановка ядра, застрявшего в `dsb sy` внутри
`deleteASID()`, вообще не берётся JTAG'ом — известная и подтверждённая
на этом железе ситуация (см. `../../old/situation.usb.old.txt`).

**Как встать в U-Boot.** `CONFIG_BOOTDELAY=2` (проверено в
`/home/nikita/u-boot/.config:445`) — две секунды на нажатие клавиши в
UART-консоли. Успеть можно, но каждый раз нервно.

Разово увеличить окно, **не пересобирая u-boot.bin**: в конфиге стоит
`CONFIG_ENV_IS_IN_FAT=y`, `CONFIG_ENV_FAT_DEVICE_AND_PART="0:1"`,
`CONFIG_ENV_FAT_FILE="uboot.env"` (`.config:895-906`) — то есть `saveenv`
работает и переживает выключение, окружение ложится файлом `uboot.env` на
ту же FAT-партицию BOOT:

```
U-Boot> setenv bootdelay 10
U-Boot> saveenv
```

Вернуть обратно — `setenv bootdelay 2; saveenv`. Обычная загрузка с карты
из приглашения — команда `boot`.

> `bootdelay -1` (никогда не грузиться самому) ставить **не стоит**:
> если UART-консоль окажется недоступна, плата больше не поднимется
> вообще, а `uboot.env` лежит на карте, которую придётся вынимать.
>
> Ещё: `uboot.env` живёт на партиции BOOT. Если `rt/flash.sh` переливает
> её целиком, `bootdelay` вернётся к 2 — тогда `saveenv` повторить.

## 5. Что этот способ обновляет, а что нет

Тут легко обмануться и полдня искать, почему правка «не приехала».
Проверено по `projects/sel4test/apps/sel4test-driver/CMakeLists.txt:89-113`
(секция `pack_vfs.sh` / `archive.cpio`) и по `build_and_sign.sh`.

**Внутри образа (обновляется через JTAG):**

| Что | Откуда в образе |
|---|---|
| `kernel.elf` (seL4) | elfloader'ский CPIO |
| `sel4test-driver` (rootserver, `main.cpp`) | он же |
| `uart_driver`, `timer_driver`, `shell` | `file_list.txt` → `archive.cpio`, вшит в rootserver |
| `blk_driver`, `net_driver`, `usb_driver` | там же |

**Снаружи, на exFAT-партиции RPI (через JTAG НЕ обновляется):**

| Что | Куда кладёт `build_and_sign.sh` |
|---|---|
| `wifi_driver` | `/service/wifi.elf` |
| все `/sbin`-команды (`sb_*`) | `/sbin/*.elf` |
| тестовые утилиты (`sbtest_*`, в т.ч. `coretest`/`hotplugtest`) | `/sbin/tests/*.elf` |
| `balancer` | `/service/balancer.elf` |
| `test_app` | `/bin/test_app.elf`, `/root/test_app.elf` |
| `/etc/init.conf`, `/etc/auto_restart.conf` | правятся прямо на устройстве |

То есть: правки в ядре, rootserver'е, шелле и шести основных драйверах
— доезжают. Правки в wifi-драйвере, любой `/sbin`-команде или тесте —
**нет**, для них по-прежнему нужна карта. Скрипт печатает об этом
напоминание после каждого запуска.

## 6. Способ A — скрипт (основной)

Предусловия: JTAG поднят по `../debug_of_FT232H/`, работают обе задачи
VSCode (`JTAG: SSH-туннель (carto)` и OpenOCD на carto), плата стоит в
приглашении U-Boot (§4).

```bash
cd /home/nikita/psych-ward-os
uart_wifi_JTAG/load_over_JTAG/file/jtagload.sh -b     # -b = сначала собрать
```

Что делает по шагам:
1. (`-b`) `./build_and_sign.sh`.
2. Раскладка на `carto:~/jtag/` — **OpenOCD запускается там и читает файлы
   своей файловой системой**, здешние пути ему не годятся. Скрипт возит
   и конфиги OpenOCD (`ft232h-jtag.cfg`, `ft232h-jtag-load.cfg`), и сам
   образ (`psych-ward-os.bin`). Конфиги обновляются при каждом запуске:
   они по 2-3 КБ, на фоне 1.9 МБ образа не заметны, зато carto никогда не
   отстаёт от репозитория. Каноничные копии живут здесь, в git; на carto
   их править нельзя — затрёт следующий запуск.
3. Через telnet-консоль OpenOCD (порт 4444, уже проброшен туннелем):
   `targets bcm2711.cpu0` → `halt` → `load_image ... 0x10000000 bin`.
4. `reg pc 0x10000000`, `reg x0 0`, `reg x1 0`, `resume`.

Полезные режимы:

```bash
jtagload.sh --provision   # только разложить конфиги на carto (первичная настройка)
jtagload.sh -n            # на carto всё актуально, ничего не копировать
jtagload.sh --load-only   # залить, но не запускать (cpu0 останется halted!)
jtagload.sh --run-only    # не заливать, только перезапустить уже залитое
jtagload.sh --resume      # СПАСЕНИЕ: резюмнуть забытый halted cpu0
jtagload.sh --halt        # просто остановить cpu0
```

`jtagload.sh` использует `file/jtag_ocd.py` — маленький клиент telnet-консоли
OpenOCD. Он нужен вместо привычного `echo ... | nc localhost 4444` (приём
из `../debug_of_FT232H/FT232H-jtag-guide.md`, §6) по одной причине:
`load_image` на 1.9 МБ держит консоль десятки секунд, а `nc` закрывает
сокет сразу по концу stdin — OpenOCD получал бы EOF посреди заливки.
Клиент держит соединение до маркера, который OpenOCD печатает последней
командой (`echo JTAGLOAD-DONE`), и выходит ровно тогда, когда цель дошла
до конца списка.

## 7. Способ Б — из GDB (когда нужны символы с первой инструкции)

```bash
cd /home/nikita/psych-ward-os
gdb-multiarch -q -x uart_wifi_JTAG/load_over_JTAG/file/jtagload.gdb
(gdb) break continue_boot        # или любое место в elfloader/ядре
(gdb) continue
```

Скрипт делает `file build-rpi4/elfloader/elfloader` → `target extended-remote
localhost:3333` → `monitor halt` → `load` → подтягивает символы
`kernel.elf` и `sel4test-driver` → выставляет `$pc`.

Медленнее способа A (GDB бьёт запись на мелкие пакеты remote-протокола,
`load_image` этого не делает), зато сразу даёт живую сессию: можно
поставить брейкпоинт **до** старта образа и пройти bring-up по шагам —
чего при обычной загрузке с карты не сделать в принципе.

## 8. Способ В — одной командой из telnet-консоли OpenOCD

`file/ft232h-jtag-load.cfg` попадает на carto сам — любым запуском
`jtagload.sh` или отдельно через `jtagload.sh --provision`. Дальше OpenOCD
запускается с ним (`openocd -f ft232h-jtag-load.cfg` — второй `-f` не нужен,
`board/rpi4b.cfg` подтягивается изнутри), и в telnet-консоли доступны:

```bash
nc localhost 4444
> psych_boot          # halt + load_image + reg pc + resume
> psych_load          # только залить
> psych_run           # только запустить залитое
> psych_rescue        # резюмнуть забытый halted cpu0
```

Образ при этом должен уже лежать на carto (`~/jtag/psych-ward-os.bin`) —
копирование остаётся за `jtagload.sh -n`/`scp`. Способ удобен, когда
хочется перезапустить один и тот же образ несколько раз подряд.

## 10. Безопасность: этот путь обходит Фазу 13 целиком

Сказать прямо, чтобы потом не было сюрприза: заливка через JTAG **не
проходит проверку подписи FIT/RSA**. U-Boot в этой схеме вообще не
участвует в загрузке образа — он только держит машину в известном
состоянии. Значит:

- Ed25519-подпись `/sbin`, `/service` (Фаза 12) продолжает работать как
  обычно — она проверяется rootserver'ом, а эти файлы лежат на карте и
  через JTAG не меняются.
- RSA-подпись загрузочного образа (Фаза 13) **не проверяется**. Это
  осознанная плата за скорость итерации в разработке и ещё одна причина
  не оставлять JTAG подключённым к чему-либо, кроме своего стенда.
- Прогон, который должен подтвердить работу secure boot, обязан идти
  через карту. Финальную проверку перед «закрытием фазы» делать только
  штатным путём.

## 11. Известные питфолы и что проверить первым

| Симптом | Причина / что делать |
|---|---|
| `jtag_ocd.py: не могу подключиться к localhost:4444` | Не поднят SSH-туннель или OpenOCD на carto. Порядок — как в `../debug_of_FT232H/`, §6. |
| После заливки плата молчит, UART пуст | Скорее всего плата НЕ стояла в приглашении U-Boot (§4). Проверить: `mdw 0x10000000 4` через консоль 4444 — там должны быть первые слова образа (`0xd5034fdf ...`). |
| Всё зависло сразу после `resume` | **[гипотеза]** ядра 1-3 были не в spin-table (плата уже успела загрузить старую ОС). Лечится только перезагрузкой платы и повторным входом в U-Boot. |
| Залилось, но ведёт себя как мусор | Гипотеза о несогласованности кэшей (OpenOCD пишет через отладочный интерфейс, а D/I-кэш U-Boot'а включён, §3) **на железе 2026-09-06 не подтвердилась**: сверка `mdw` с оригиналом в трёх точках совпала байт-в-байт. Если всё-таки столкнётесь — сначала `mdw`; если чтение верное, а исполнение нет, виноват I-кэш, и обход такой: залить через JTAG, но прыгнуть **командой U-Boot** `go 0x10000000` (`do_go_exec`, `arch/arm/lib/cmd_boot.c:33` — простой вызов, ровно то же, что делает `bootm`). |
| UART/шелл замерли, отладчик уже отключён | cpu0 остался halted. Это ОБЩЕЕ правило всего JTAG-стека, а не особенность этой методички: **всегда resume перед отключением**. Спасение: `jtagload.sh --resume` или `psych_rescue`. Подробности — `../debug_of_FT232H/FT232H-jtag-guide.md`, §6 «КРИТИЧНО». |
| Правил `~/jtag/*.cfg` прямо на carto — правка исчезла | Так и задумано: каноничные копии лежат в репозитории (`debug_of_FT232H/file/`, `load_over_JTAG/file/`), `jtagload.sh` перезаписывает ими carto при каждом запуске. Править — только здесь. |
| Правка «не приехала» | Проверить по §5, не лежит ли изменённый файл на карте, а не в образе. Классика: любая утилита из `/sbin/tests/`. |
| Приглашение U-Boot замерло сразу после старта OpenOCD | Ожидаемо по `../debug_of_FT232H/`, §6 (OpenOCD останавливает cpu0 самим фактом старта). Но 2026-09-06 этого НЕ произошло — все 4 ядра остались `running`. Поведение НЕ гарантированное в обе стороны: проверять `targets`, а не предполагать. |
| `load_image` идёт мучительно долго | 4000 кГц — проверенная на железе скорость. Поднимать (закомментированная строка в `ft232h-jtag-load.cfg`) только с короткими проводами и обязательно с проверкой чтением обратно. |
| Залили один образ, а символы в GDB от другого | `jtagload.sh` предупреждает, если `elfloader` новее плоского образа. Оба берутся из одного `build-rpi4/`, расхождение означает, что `ninja` не отработал. |

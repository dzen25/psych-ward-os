## Фаза 0 — Подготовка

Все платформо-зависимые адреса (UART/RTC/virtio-mmio, регистры PL031, GIC IRQ) вынесены в `src/h/platform.h`; убедились, что рефактор не сломал поведение на QEMU (boot/shell/net/disk/NTP). Заодно задокументирован quirk `timer_driver.cpp`: offset `0x10` использовался под именем «ICR» для PL031, хотя по датащиту это IMSC (реальный ICR — `0x1C`) — трогать не стали, поскольку весь этот код позже целиком ушёл при замене на ARM generic timer (Фаза 3.1).

## Фаза 1 — Hello World на живом железе

Собрана цепочка загрузки RPi4 (GPU firmware → device tree → `config.txt` → U-Boot → seL4-образ), установлена связь по UART через serial-консоль (GPIO 14/15, USB-UART, 3.3V), подтверждён ручной запуск на живой плате, автоматизирована загрузка через `boot.scr`. Всё проверено на тестовой hello-world сборке, отдельно от кода `psych-ward-os`.

Файлы цепочки лежат в [`load_chain_test/`](load_chain_test) (финальные образы — в [`load_chain/`](load_chain)): `start4.elf`, `fixup4.dat`, `bcm2711-rpi-4-b.dtb`, `config.txt`, `u-boot.bin`, `sel4test-driver-image-arm-bcm2711`. Скрипт автозагрузки — `boot.cmd`, скомпилированный в `boot.scr` (`mkimage`), лежит в корне FAT32-раздела SD-карты.

<details>
<summary><b>Как устроена цепочка загрузки, шаг за шагом (клик, чтобы развернуть)</b></summary>

| # | Стадия | Файл | Источник |
|---|---|---|---|
| 1 | FSBL | — (в ROM платы) | не трогаем |
| 2 | GPU firmware | `start4.elf`, `fixup4.dat` | [raspberrypi/firmware/boot](https://github.com/raspberrypi/firmware/tree/master/boot) |
| 3 | Device tree | `bcm2711-rpi-4-b.dtb` (+ `overlays/*`) | тот же репозиторий |
| 4 | Конфиг | `config.txt` | пишем сами: `arm_64bit=1` + `kernel=u-boot.bin` |
| 5 | Bootloader | `u-boot.bin` | собираем сами |
| 6 | seL4-образ | `sel4test-driver-image-arm-bcm2711` | результат сборки sel4test |

1. **BootROM** — прошито в кристалл SoC на заводе, не на SD-карте. Читает конфигурацию из EEPROM платы, единственная задача — найти и запустить `start4.elf`. Дальше всё на GPU (VideoCore VI), ARM-ядра ещё в reset.
2. **`start4.elf` + `fixup4.dat`** — закрытая прошивка VideoCore VI. Поднимает и калибрует SDRAM (на этом этапе ARM-ядра ещё ничего не могут), читает `config.txt` и device tree с той же SD-карты. `start4.elf` — вариант под BCM2711/Pi4, `fixup4.dat` — согласованная с ним таблица разметки памяти между GPU и ARM; версии всегда брать из одного релиза, не смешивать.
3. **`config.txt`** — парсит GPU firmware (ARM его не видит). Два значимых параметра: `arm_64bit=1` (поднять ядра сразу в AArch64) и `kernel=u-boot.bin` (что считать «ядром» и передать на выполнение).
4. **`bcm2711-rpi-4-b.dtb`** — машиночитаемое описание железа платы. GPU firmware грузит его в память и передаёт указатель ARM-ядрам через регистр x0. `overlays/*` — опциональные фрагменты под конкретную HAT-периферию, для базового boot не нужны.
5. **GPU firmware выпускает ARM-ядра из reset**, передаёт управление по адресу `kernel=` (обычно физический `0x80000`) с указателем на dtb в x0 — протокол загрузчика Linux-стиля, U-Boot тоже так собран.
6. **`u-boot.bin`** — реально первое, что исполняется на ARM. seL4-образ нельзя указать напрямую в `kernel=` (GPU firmware понимает только zImage/Image-подобные загрузчики) — U-Boot даёт консоль и команды `fatload`/`go`, чтобы положить seL4-образ по адресу `0x10000000` и прыгнуть туда.
7. **`sel4test-driver-image-arm-bcm2711`** (после Фазы 3 — готовый `psych-ward-os`) — seL4-ядро + root task, один плоский бинарник. U-Boot: `fatload mmc 0 0x10000000 <образ>` → `go 0x10000000`.

**Сборка U-Boot:**
```bash
git clone https://github.com/u-boot/u-boot.git u-boot && cd u-boot
make CROSS_COMPILE=aarch64-linux-gnu- rpi_4_defconfig
make CROSS_COMPILE=aarch64-linux-gnu-
# результат: u-boot.bin
```

**Сборка sel4test под rpi4** (в отдельном дереве, не в `psych-ward-os`):
```bash
mkdir -p ~/sel4-rpi4-hello && cd ~/sel4-rpi4-hello
repo init -u https://github.com/seL4/sel4test-manifest.git && repo sync
mkdir cbuild && cd cbuild
../init-build.sh -DPLATFORM=rpi4 -DAARCH64=1 -DRPI4_MEMORY=<реальный RAM платы>
ninja
```
⚠️ Если `-DRPI4_MEMORY` не указать — по умолчанию считает 8GB, на плате с меньшим объёмом загрузка может падать. Всегда указывать реальный объём.

**Автозагрузка** (`boot.cmd`, вместо `setenv bootcmd; saveenv`, который прячет конфиг в бинарный `uboot.env` — версионируемый скрипт лучше):
```
fatload mmc 0 0x10000000 sel4test-driver-image-arm-bcm2711
go 0x10000000
```
```bash
mkimage -A arm64 -O linux -T script -C none -d boot.cmd boot.scr
```
`boot.scr` в корне SD-карты — U-Boot подхватывает его автоматически.

## Фаза 2 — Извлечение адресов под свои драйверы

seL4 на rpi4 уже знает адреса UART/GIC/generic timer — из dtb их вытаскивать не нужно. DTB понадобился только под железо, которого в seL4 нет «из коробки»: декомпилирован `bcm2711-rpi-4-b.dtb` (`dtc -I dtb -O dts ...`), найдены узлы `genet` (Ethernet MAC) и EMMC2 (SD-контроллер) — адреса и IRQ занесены в rpi4-секцию `src/h/platform.h`.

## Фаза 3 — Порт дерева `psych-ward-os`

Создана ветка `RPi4`, дерево пересобрано с `-DPLATFORM=rpi4 -DRPI4_MEMORY=...` без правок `easy-settings.cmake`/`init-build.sh` (платформа нигде не захардкожена).

### 3.1 — ARM generic timer вместо PL031

Battery-backed RTC (PL031) на стоковой плате физически нет. Аптайм переведён на прямое чтение `CNTVCT_EL0`/`CNTFRQ_EL0` из EL0 (без трапа в ядро — `gen_config.yaml` этой сборки разрешает `EXPORT_VCNT_USER`). Wall-clock время решили брать только из NTP (I2C RTC-модуля на плате нет); без сети при старте offset остаётся 0 — принятая деградация, не баг. Подтверждено на живом железе (`time`/`uptime`/`sleep`).

### 3.2 — GENET вместо virtio-net

`net_driver.cpp` полностью портирован на GENET v5 (BCM2711 Ethernet MAC, RGMII PHY) — DMA-кольца TX/RX, MDIO, автосогласование скорости с реальным чтением результата (не хардкод), по образцу проверенного U-Boot-драйвера этой же платы. Поверх аппаратного слоя (ARP/IPv4/UDP/DNS/NTP-логика, которая переиспользовалась как есть) добавлен полноценный DHCP-клиент — получение IP/шлюза/маски/DNS вместо захардкоженных QEMU-адресов (`10.0.2.15`/`10.0.2.2`), обработка входящих ARP-запросов на собственный адрес (без неё соседи по сети со временем теряли нас из своего ARP-кэша и переставали быть в состоянии достучаться), прямой резолв MAC соседей по своей подсети вместо всегда-через-шлюз, честная разборка DNS-ответов (сервер не обязан сжимать имена, а не только по указателю), и правильная работа с некэшируемой DMA-памятью (кэш-когерентность между CPU и GENET). Подтверждено на живом железе: DHCP, ARP, ping до локальных и внешних хостов (вывод в формате обычного unix `ping`, со статистикой в конце), резолвинг доменов через DNS, NTP-синхронизация. Аппаратная граница вынесена в отдельный интерфейс (`net_hw_init/send/poll_rx/rx_done`), чтобы будущий Wi-Fi-бэкенд (Фаза 4) мог подключиться на то же место — заготовка в `wifi_driver.cpp`.

### 3.3 — EMMC/SD вместо virtio-blk

`blk_driver.cpp` портирован на реальный EMMC2 (Arasan SDHCI) — инициализация, чтение/запись блоков; FAT32-логика поверх переиспользована как есть. По пути найден и обойдён MBR на реальной SD-карте (раздел начинается не с нулевого сектора, в отличие от тестовых QEMU-образов) и восстановление `CONTROL0` после software reset (SRST_HC сбрасывает биты питания шины, недокументированная особенность контроллера). Подтверждено на живом железе: `ls`/`cat`/`touch`/`echo`/`mkdir`, несколько циклов перезагрузки подряд.

### 3.4 — UART / GIC

Только смена адресов в `platform.h`, логика не менялась — RPi4 использует GICv2 и PL011-совместимый UART0, те же, что и на QEMU. Boot readiness протокол (`SYS_DRIVER_READY`/`SYS_WAIT_ALL_DRIVERS_READY`) подтверждён со всеми живыми драйверами (timer/EMMC/GENET).

## Фаза 4 — Wi-Fi (BCM43455)

На RPi4 Wi-Fi обслуживается отдельным SDIO-хостом (`mmc@7e300000`, DT compatible `brcm,bcm2835-sdhci`) — не тот же контроллер, что EMMC2 (Фаза 3.3, `brcm,bcm2711-emmc2`), хотя регистровый layout — тот же стандартный SDHCI Simplified Spec. Поверх SDIO-транспорта живёт проприетарный протокол Broadcom (`brcmfmac` в Linux: backplane/core enumeration, загрузка прошивки/NVRAM, sdpcm-кольцо, CDC/BDC IOCTL) — по эталонному исходнику ядра это ~9-10 тысяч строк, на порядок больше GENET и EMMC2 вместе взятых, поэтому реализация разбита на милстоуны, а не делается одним заходом.

### 4.1 — SDIO host bring-up (done, подтверждено на живом железе)

`wifi_driver.cpp` — отдельный процесс (`is_driver = 5`, свой командный IPC-канал шелл↔драйвер по образцу `net_cmd_*`, печатает `ready` наравне с остальными драйверами), поднимает SDIO-хост-контроллер и проводит полную идентификационную последовательность карты BCM43455: software reset → идентификационный клок → CMD5 (`SDIO_SEND_OP_COND`, с повтором до бита ready, как ACMD41 в `blk_driver.cpp`) → CMD3 (получить RCA) → CMD7 (выбрать карту) → CMD52 (`SDIO_RW_DIRECT`, чтение F0 CCCR-регистра). Порядок команд сверен с эталонным Linux MMC core (`drivers/mmc/core/sdio.c::mmc_sdio_init_card`) — CMD52 не проходит, пока карта не выбрана через CMD3/CMD7. Низкоуровневые SDHCI-хелперы — перенос из `blk_driver.cpp` (тот же регистровый layout). Выключено по умолчанию (`RPI4_ENABLE_WIFI = false` в `main.cpp`); не блокирует загрузку остальных драйверов/шелла. Диагностика — команда шелла `wifiprobe`.

Подтверждено на живом железе: `CMD5 OCR=0xb0ffff00` → `CMD3 RCA=0x00010000` → CMD7 выбрал карту → `CMD52 F0 CCCR=0x32` (реальная, осмысленная версия CCCR/FBR чипа, не мусор) — SDIO-хост и полная транзакционная цепочка с чипом подтверждены.

По пути найдены и исправлены три независимых бага общего характера (не специфичных для WiFi, подробности и уроки на будущее — в памяти проекта):
1. **`alloc_device_frame()` (`main.cpp`)** — bump-allocator по возрастанию физических адресов молча отдавал чужой фрейм, если новый `target_paddr` оказывался позади уже продвинутого watermark'а того же untyped-региона (WiFi и EMMC2 делят один регион). Добавлена жёсткая проверка-паника + аллокации переупорядочены.
2. **Exclusive-инструкции (`__sync_lock_*`) на некэшируемой Device-памяти** — компилируются в LDXR/STXR, которые на Device-памяти по спеке ARM непредсказуемы и на практике уронили весь kernel seL4 (`halting... Kernel entry via Unknown (0)`). Заменено на обычный volatile-флаг (система однопроцессорная, `SMP OFF` — hardware-atomic не нужен).
3. **Рассинхронизация атрибутов кэширования одной и той же физической SHM** — `rootserver_shm_base` мапился кэшируемым, а все остальные процессы видят ту же память некэшируемой, из-за чего `ps` показывал устаревшие данные. Экспериментальная попытка сделать оба маппинга некэшируемыми сама сломала `strcpy()` (Alignment Fault) — итоговое решение: оставить кэшируемым и явно сбрасывать кэш (`flush_rootserver_shm()`) в местах обмена данными с некэшируемыми читателями/писателями.

### 4.2 — backplane enumeration + прошивка/NVRAM (done, подтверждено на живом железе)

Между Милстоуном 4.1 (SDIO-транспорт) и настоящим сетевым протоколом чип нужно
разбудить: найти его внутренние ядра на backplane-шине, остановить ARM-ядро,
залить прошивку (`~630KB`) и NVRAM (`~1.9KB`, вариант `raspberrypi,4-model-b`
— уже разжаты и лежат в `load_chain/wifi_fw.bin`/`wifi_nvram.txt`) в RAM чипа
и запустить. Всё сверено построчно с эталонным `chip.c`/`sdio.c`/`bcmsdh.c`
(два параллельных агента-исследователя + прямая проверка констант) для
чипов семейства `0x4345` — адреса/биты не догадки:

- **Backplane-окно** — 32KB-окно на SDIO-функции 1 (`SBSDIO_FUNC1_SBADDR{LOW,MID,HIGH}`),
  доступ к внутренней шине чипа только через него; `backplane_read32/write32`
  через CMD53 (не CMD52 — тот только байтовый), PIO-цикл 1:1 по образцу
  `hardware_emmc_read/write` в `blk_driver.cpp`.
- **EROM (Enumeration ROM)** — chipcommon на фиксированном адресе
  `0x18000000`, дальше перечисление остальных ядер по таблице дескрипторов
  (`eromptr`, offset `0xFC`) — находим `base`/`wrap` для ARM CR4 (`0x83E`) и
  D11/802.11 MAC (`0x812`), больше ничего не нужно.
- **Halt/reset** — CR4 останавливается (вне reset, но halted — иначе гонка с
  собственным исполнением при заливке в TCM), D11 сбрасывается, тем же
  общим `wifi_core_reset()` (перенос `brcmf_chip_ai_coredisable`+`ai_resetcore`).
  RAM-адрес (`0x198000`) — хардкод для чипа `0x4345`, реальный размер RAM —
  читается динамически (`ARMCR4_CAP/BANKIDX/BANKINFO`).
- **Заливка** — блоками до 4096 байт (64 блока по 64 байта, настоящий CMD53
  block-mode, с учётом границ 32KB-окна), NVRAM — не следом за прошивкой, а
  в самом верху RAM (`rambase+ramsize-len`), с 4-байтовым трейлером-версией
  (`(~len/4<<16)|(len/4&0xFFFF)`).
- **Старт** — reset vector (первые 4 байта прошивки) пишется по
  backplane-адресу `0`, затем CR4 снимается с halt.
- **Смок-тест без sdpcm-кольца** (это уже 4.3) — читаем `sdpcm_shared`
  (указатель в самом верху RAM, `rambase+ramsize-4`) и, если валиден, дальше
  `rte_console` — если в логовом кольцевом буфере прошивки видно похожее на
  текст, прошивка точно исполняется.

Диагностика — та же команда `wifiprobe`, добавлены два новых поля
(`Firmware: ALIVE/not alive`, `shaddr`).

**Подтверждено на живом железе**: полный EROM-скан (`chipid=0x15264345`,
CR4/D11 `base`/`wrap` найдены), halt CR4/reset D11, заливка прошивки
(`0x9d243` байт) и NVRAM (`0x6b0` байт), запуск CR4, и — главное —
`sdpcm_shared`/`rte_console` реально читаются из RAM чипа и в них виден
живой текст прошивки:
```
wl0: Broadcom BCM4345 802.11 Wireless Controller 7.45.234 (4ca95bb CY)
TCAM: 256 used: 254 exceed:0
```
Прошивка BCM43455 действительно исполняется на живом железе — не просто
"чип отвечает на команды", а полноценный код прошивки поднялся и работает.

По пути найдено и исправлено ещё несколько багов (все — в новом коде этого
милстоуна, не общие для проекта, но поучительные для будущей работы с SDIO):

1. **Не включена SDIO-функция 1 перед использованием.** CMD52/CMD53 к
   функции 1 (backplane) не проходили, пока не выставлен бит функции в
   CCCR `IOEx` (offset `0x02`) и не дождались того же бита в `IORx` (offset
   `0x03`) — отдельный от CMD3/CMD7 шаг, специфичный именно для SDIO-функций
   (см. `sdio_enable_func1()`).
2. **Не запрошена тактовая частота самого чипа.** Одиночные регистровые
   CMD52/53-обращения (chipid/eromptr/halt/reset/ramsize) чип обслуживал и
   так, но настоящая bulk-передача (заливка прошивки) зависала на стороне
   чипа без ответа (`DATA_DONE` никогда не приходил), пока не запрошен и не
   подтверждён ALP через `SBSDIO_FUNC1_CHIPCLKCSR` (offset `0x1000E`, см.
   `wifi_request_alp_clock()`/эталонный `brcmf_sdio_buscoreprep()`). HT
   специально НЕ запрашивается на этом шаге — эталонный
   `brcmf_sdio_firmware_callback()` явно ставит `alp_only=true` именно на
   время заливки прошивки, HT нужен только позже, для data-path.
3. **Не согласован размер блока функции 1.** Реальный драйвер один раз
   вызывает `sdio_set_block_size(func1, 64)` (CMD52 в FBR-регистр `0x110`,
   с функцией **0**, а не 1 — FBR общий, не в адресном пространстве самой
   функции) перед любыми bulk-передачами — без этого шага заливка крупных
   кусков возвращала Data CRC Error.
4. **CMD53 без `EMMC_TM_MULTI_BLOCK`/`BLKCNT_EN` в CMDTM хоста.** Флаг
   block-mode в САМОМ аргументе CMD53 (виден только карте) — не то же
   самое, что флаги Transfer Mode в регистре CMDTM хост-контроллера: без
   них контроллер игнорировал блок-каунт из `BLKSIZECNT` и завершал
   передачу после ПЕРВОГО блока. Раньше в проекте не было ни одного
   настоящего multi-block переноса (`blk_driver.cpp` намеренно гоняет
   SD-сектора по одному, CMD17/24), поэтому баг всплыл впервые именно тут.
   Buffer Write Ready при этом — событие НА КАЖДЫЙ блок, а не на весь
   перенос сразу.
5. **PIO пишет словами, а длина файла произвольная.** Хвост данных короче
   4 байт (у прошивки — ровно 3 байта) при целочисленном делении
   `len/4=0` не писал в FIFO вообще ничего, и контроллер зависал в
   ожидании данных, которые никто не подложил — исправлено дополнением
   буфера прошивки нулями до кратности 4 перед заливкой.
6. **SDIO-шина всё время на делителе идентификационной стадии.** После
   CMD7 (карта выбрана) клок так и остался на ~390кГц вместо рабочей
   скорости — заливка ~630KB работала, но заметно медленно. Поднято до
   делителя `0x02` (~25МГц), как и `blk_driver.cpp` делает для EMMC2 после
   своего CMD7.

### 4.3 — sdpcm/IOCTL (✅ подтверждено на живом железе)

sdpcm-кольцо (SDIO Function 2, 12-байтный software-заголовок) и CDC/BDC
IOCTL-канал поверх него. Успешный смок-тест: `BRCMF_C_GET_VERSION` (raw dcmd)
и iovar `"ver"` (`BRCMF_C_GET_VAR`) вернули настоящую строку версии прошивки
через нормальный протокольный канал (а не через отладочный `rte_console`-дамп,
как в 4.2): `"wl0: Apr 15 2021 03:03:20 version 7.45.234 (4ca95bb CY) FWID
01-996384e2"`.

По пути найдено и исправлено несколько нетривиальных багов:
1. **`sdio_enable_func()` перезаписывал CCCR IOEx (offset 0x02) одним битом
   новой функции БЕЗ read-modify-write** — CMD52-запись всегда перезаписывает
   байт целиком (аппаратного OR нет), поэтому `sdio_enable_func(F2)` писал
   `0x04` и СБРАСЫВАЛ уже включённый бит функции 1 (`0x02`). Это был
   настоящий root cause целой серии казавшихся не связанными симптомов:
   прямые F1 CMD52 (WATERMARK/CHIPCLKCSR-restore/MESBUSYCTRL) стабильно
   ловили Command Timeout, а чуть позже — и backplane-чтения (`intstatus`,
   `tohostmailboxdata`) стали ловить Data Timeout, ВСЕ сразу после enable F2,
   ВСЕ реально из-за того, что F1 оказывалась выключена. Исправлено:
   читать текущее значение IOEx и ORить новый бит перед записью.
2. **`intstatus` (`I_HMB_HOST_INT`/`I_HMB_FRAME_IND`) ненадёжно отражает
   готовность ответного кадра на этом железе** — флэтлайнил по много секунд,
   хотя кадр уже был готов и лежал в F2 (подтверждено побайтовым
   hex-dump'ом TX-кадра и точной сверкой sdpcm/BCDC заголовков с эталоном —
   протокол был верен, просто «сигнал готовности» не приходил вовремя).
   Итоговое решение: `sdpcm_wait_and_read_ctrl()` не полагается только на
   `intstatus` — вдобавок раз в ~300мс СПЕКУЛЯТИВНО пробует прямое чтение F2
   независимо от него; несовпадение чек-суммы/канала при такой попытке —
   не ошибка, а просто «кадра ещё нет».
3. **`GET_VERSION` изначально слался с `dcmd.len=0`** — для GET-команд это
   поле объявляет ёмкость буфера ПОД ОТВЕТ (а не длину payload'а запроса),
   и ноль означал «у тебя нет места под ответ». Исправлено на `len=4`
   (размер ожидаемого `uint32`), по аналогии с `"ver"` (там `len` = весь
   буфер с запасом).
4. **BCDC-ответ на устаревший (уже вышедший по таймауту) запрос может
   прийти позже и «перепутаться» с ответом на следующий** — `wifi_ioctl()`
   теперь не считает несовпадение `reqid` фатальным, а продолжает ждать
   следующий кадр (до 3 попыток), как и сам эталон
   (`brcmf_proto_bcdc_query_dcmd`).
5. Best-effort-шаги (`watermark`/`SBSDIO_DEVICE_CTL`/`MESBUSYCTRL`,
   `CHIPCLKCSR`-restore к `saveclk`, `hostintmask`) настраиваются ДО enable
   F2 — прямые F1 CMD52-записи после enable F2 продолжают быть менее
   надёжными на этом конкретном железе, хотя формально причина (п.1) уже
   исправлена; порядок пока оставлен как есть, поскольку он подтверждённо
   работает.
6. Первым control-запросом (как и в эталоне, `brcmf_sdio_bus_preinit()`)
   отправляется iovar `"bus:txglom"=0` — отключает scatter-gather TX
   glomming, которого всё равно нет в этом bare-metal порте.

### 4.4 — Подключение к точке доступа (в процессе, отлаживается на живом железе)

Подключение по SSID/WPA2-PSK. Уточнение по ходу дела: вопреки исходному
предположению выше, эталонный драйвер НЕ просит прошивку саму вывести PMK из
ASCII-пароля — PBKDF2-HMAC-SHA1(passphrase, SSID, 4096 итераций) выполняется
на хосте (см. `wifi_pbkdf2_selftest()`/`pbkdf2_hmac_sha1()` в
`wifi_driver.cpp`, сверено побайтово с `hashlib.pbkdf2_hmac`); сам 4-way
handshake и 802.11 MLME по-прежнему делает прошивка. Полная
dcmd/iovar-последовательность (`SET_INFRA`/`auth`/`wpa_auth`/`wsec`/
`sup_wpa`/`SET_WSEC_PMK`/`BRCMF_C_UP`/`PM_OFF`/`join`) реализована и
подтверждена побайтово корректной на проводе. Долгое время воспроизводился
загадочный симптом: вся последовательность ack'алась без единой ошибки, но
после `join` не приходило ВООБЩЕ НИ ОДНОГО события (ни успеха, ни ошибки) за
15с ожидания. Диагностика (слепой `escan`, не зависящий от SSID/PSK) вскрыла
настоящую причину: `status=0xfffffffc` (`BCME_NOTUP`, -4) — интерфейс
оказывался фактически "down" к моменту join. Порядок вызовов имеет значение:
`BRCMF_C_SET_INFRA` меняет режим интерфейса, и на этой прошивке это, похоже,
неявно сбрасывает интерфейс обратно в "down" — поэтому `BRCMF_C_UP` нужно
слать ПОСЛЕДНИМ, непосредственно перед `join`/`escan`, а не в начале
последовательности (как было изначально). Итог 4.4, после подтверждения
join — подключить готовый data-path к уже существующему интерфейсу
`net_hw_init/send/poll_rx/rx_done` в `net_driver.cpp`, чтобы вся текущая
протокольная логика (ARP/DHCP/DNS/ping) заработала над Wi-Fi без правок
(ещё не сделано).

#### 4.4.1 — Ручной жизненный цикл wifi_driver + знакомые сети

`wifi_driver` **больше не спавнится при загрузке** (main.cpp: `RPI4_ENABLE_WIFI`
теперь означает только "ресурсы/эндпоинты скомпилированы", а не "процесс
запущен") — есть подозрение, что одновременный спавн вместе с остальными
драйверами вызывал гонку мапинга/таймингов, изредка ломавшую готовность
sdpcm-канала (см. интермиттентный краш на настройке CR4 в записях по
Милстоуну 4.2 выше). Теперь это отдельная, изолированная от общего бута
операция:

- Три новых сисколла в `common.h`, по образцу `SYS_EXEC`/`SYS_KILL`/
  `SYS_RECOVER`: `SYS_START_WIFI` (спавнит `wifi_driver`, если ещё не
  запущен), `SYS_STOP_WIFI` (убивает БЕЗ автореспавна — в отличие от
  `SYS_KILL`/`SYS_RECOVER`/watchdog, где респавн критичных компонентов
  всегда желателен), `SYS_WIFI_STATUS` (0=не запущен/1=запущен, не готов/
  2=готов принимать команды — держится в `g_wifi_driver_ready`,
  выставляется в `case SYS_DRIVER_READY` для `is_driver==5`).
  `generic_recover_process()` получил параметр `respawn` (по умолчанию
  `true`, чтобы не менять поведение существующих вызовов), чтобы
  `SYS_STOP_WIFI` мог переиспользовать её же логику очистки capability без
  автозапуска заново.
- Шелл: `wifi start/stop/restart [-l]` — start/restart возвращаются сразу
  же, не дожидаясь готовности (собственные логи бринг-апа `wifi_driver`
  печатаются в ту же консоль независимо); `-l` дополнительно ждёт (до ~20с)
  и печатает финальный статус. Любая команда, зовущая `wifi_ep`
  (`wifiprobe`/`wifi scan`/`wifi connect`), теперь ПРОВЕРЯЕТ
  `SYS_WIFI_STATUS == 2` перед `seL4_Call` — раньше `wifi_driver` был
  гарантированно жив к моменту, когда шелл печатал приглашение, теперь это
  не так, и без проверки такой вызов завис бы навсегда.
- `wifi scan [-l]` (новая команда, `WIFI_CMD_SCAN=3` в `wifi_driver.cpp`) —
  переиспользует уже существовавший диагностический слепой `escan` из 4.4:
  печатает сырые `event_type`/`status`, БЕЗ декодирования списка SSID/BSS
  (парсинг `wl_escan_result_t`/`bss_info` — отдельная задача на будущее).
- Знакомые сети: `wifi connect <ssid> [password] [-l] [&&save]` — пароль
  теперь необязателен, если сеть уже сохранена; `&&save` сохраняет/обновляет
  пароль сети в `/wifi/pqw.txt` (формат `имясети|пароль`, по строке на
  сеть). `wifi clean [-l]` убирает текущее подключение (SSID последнего
  успешного `connect` этой сессии, `g_wifi_current_ssid` в `shell.cpp`) из
  файла; `wifi clean all [-l]` стирает файл целиком. Файл проверяется/
  создаётся (`SYS_TOUCH`) при `wifi start`/`wifi connect`, если отсутствует.
  Вся файловая работа — в `shell.cpp` (НЕ в `wifi_driver.cpp`), через тот же
  синхронный `blk_ep`-протокол (`SYS_TOUCH`/`SYS_READ_TEXT_FILE`/
  `SYS_WRITE_FILE`), что уже использовали `touch`/`cat`/`echo >`, и на той
  же некэшируемой SHM (`shm_base`, `map_frame_robust()` в `main.cpp`), что и
  передача SSID/пароля в `wifi_driver.cpp` — блокирует только обработчик
  самой команды `wifi ...` в шелле (однопоточном, обрабатывает одну команду
  за раз в любом случае), а не фоновый цикл какого-то ДРУГОГО процесса, как
  это было с `net_driver.cpp` (там помогал паттерн `seL4_Send`+mailbox+
  таймаут) — поэтому здесь он не понадобился.
- `LOG_WIFI` (`platform.h`, `true` по умолчанию) — по аналогии с
  `LOG_BLK`/`LOG_NET`, гасит НОВЫЕ диагностические сообщения (`wifi scan`);
  старый обильный вывод бринг-апа 4.1-4.3 сознательно не тронут (см. решение
  "оставить как есть" выше).

### 4.5 — Реальные IRQ вместо busy-poll — по всем драйверам, не только Wi-Fi (план, не начато)

Милстоуны 4.1-4.4 сознательно сделаны через чистый polling статусных
регистров (busy-loop с честным wall-clock таймаутом) и PIO (слово-за-словом
через EMMC_DATA) — это проще и было достаточно, пока речь шла о разовых
bring-up-операциях (регистры/прошивка/один IOCTL). Но этот же
busy-poll/`seL4_Yield()`-паттерн разъехался по всему дереву процессов, а не
только по wifi_driver — из-за него в системе почти всегда есть готовый к
выполнению поток, планировщик никогда не отдаёт CPU в WFI-простой, и плата
жрёт постоянные ~5 Вт даже когда реально нечего делать. Так работают и
готовые системы с прерываниями (Linux `brcmfmac` и т.п.) — там вся
синхронизация построена на реальных IRQ и DMA, busy-loop нет вообще.

Известные места, требующие замены polling → IRQ/Notification:

- **`shell.cpp`** — главный цикл чтения ввода (`while(1) { c = uart_getc();
  if (c == -1) seL4_Yield(); ... }`) вместо блокирующего ожидания
  IPC-нотификации от UART-драйвера при приходе символа. Туда же
  `sys_sleep()` — сейчас busy-loop с постоянным опросом `SYS_GET_TIME` через
  `seL4_Yield()`, вместо ожидания на таймерном прерывании; `SYS_SLEEP` в
  ядре (`main.cpp`) сейчас вообще заглушка ровно по этой причине (нет
  аппаратного будильника с EL0, см. комментарий там же) — без доработки
  таймерного драйвера нормальный событийный `sys_sleep()` не сделать.
- **`blk_driver.cpp`** — `emmc_wait_cmd_ready()`, `emmc_wait_dat_ready()` и
  `emmc_wait_irpt_bit()` крутятся на опросе `EMMC_STATUS`/`EMMC_INTERRUPT` с
  `seL4_Yield()` в busy-loop вместо ожидания EMMC2 IRQ через GIC (по образцу
  UART/GIC из `3.4`).
- **`net_driver.cpp`** — главный цикл (`while(1) { net_check_link_status();
  net_check_dhcp(); net_poll(); ...; seL4_Yield(); }`) поллит приём кадров
  GENET (`net_hw_poll_rx()`) на каждой итерации вместо того, чтобы спать на
  Notification, которую взводит обработчик RX IRQ.
- **`wifi_driver.cpp`** — уже описанный ниже busy-loop в
  `sdpcm_wait_and_read_ctrl()` вместо OOB GPIO `wl_host_wake` / in-band SDIO
  IRQ по линии DAT1.

Для Wi-Fi конкретно (исходный план этого пункта):

- Регистрация обработчика прерывания через seL4 IRQ-capability на GIC
  (по образцу того, как это уже сделано для других периферийных IRQ в
  проекте — см. `3.4 — UART/GIC`).
  Размаскирование CCCR `IENx` (0x04, функция 0) — включить сигнализацию
  прерывания по DAT1 на стороне карты (сейчас сознательно не трогается,
  см. комментарии в `wifi_sdpcm_bringup()`).
- Замена busy-loop в `sdpcm_wait_and_read_ctrl()` на ожидание seL4
  Notification, которую взводит IRQ-обработчик — сама передача кадра
  становится событийной, а не поллингом с фиксированным таймаутом.
- DMA (ADMA2) вместо PIO для больших пересылок (прошивка/NVRAM уже сейчас,
  и в целом data-path после 4.4) — меньше нагрузка на CPU и меньше шансов
  словить таймаут на длинных пересылках, которые сейчас идут словом за
  словом через `EMMC_DATA`. То же соображение про ADMA2 применимо и к EMMC2
  в `blk_driver.cpp`.

Важно: для Wi-Fi это хардening/производительность, а не блокер — 4.3 уже
доказан на чистом polling (см. список багов выше). Единственный из старых
блокеров, чья причина осталась не до конца понятой — прямые F1 CMD52-записи
после enable F2 (watermark/MES и т.п.) менее надёжны, чем хотелось бы, даже
после фикса `sdio_enable_func()`; сейчас это обходится порядком (настройка
до enable F2), и реальный IRQ/DMA переход, возможно, заодно уберёт и этот
обходной путь.

Отдельно от IRQ: даже после перевода всех циклов на блокирующее ожидание,
CPU всё ещё будет постоянно на максимальной частоте/напряжении — см. `4.6`
ниже, это отдельная задача, не покрытая этим пунктом.

### 4.6 — DVFS/cpufreq: снижение частоты/напряжения ARM-ядер в простое (план, не начато)

Сейчас в проекте нет вообще никакого драйвера управления частотой/напряжением
CPU — ядра остаются на той частоте/turbo-режиме, в которые их выставляет
загрузчик (VideoCore firmware/u-boot) при старте, и это состояние никогда не
меняется. В сочетании с busy-poll циклами из `4.5` (которые не дают
планировщику зайти в WFI-простой) это даёт постоянные ~5 Вт потребления даже
когда система реально ничего не делает.

Важное отличие BCM2711 от типичного ARM/x86 с cpufreq: частотой и
напряжением ARM-ядер управляет не сам ARM-кор через доступные ему MMIO/MSR
регистры, а VideoCore (VPU) — то есть единственный штатный путь сделать
DVFS — это property-tag запросы через VideoCore mailbox (`TAG_SET_CLOCK_RATE`
для ARM-клока, `TAG_GET_MIN/MAX_CLOCK_RATE`, `TAG_SET_TURBO` и т.п. — так
устроен `raspberrypi-cpufreq` в Linux). Прямых регистров, которыми ARM-ядро
само понижало бы себе частоту/вольтаж, на этом SoC нет — в отличие от
теплового сенсора (`4.3`/раздел про `temp`), который оказался читаем
напрямую по MMIO (AVS RO thermal) без прошивки VideoCore, для clock/voltage
такого альтернативного прямого пути пока не найдено.

**Известный блокер**: mailbox на этой прошивке/сборке уже пробовали — при
попытке вручную включить тактовую частоту PL011 через VideoCore mailbox
(см. `PLAT_UART_PADDR` и комментарий в `platform.h` около
`RPI4_UART1_MINIUART_PADDR`) он не ответил: STATUS/READ читались одним и тем
же неизменным значением. Если mailbox действительно не отвечает на этой
связке elfloader/прошивки в принципе (а не только для того конкретного
запроса), то DVFS через штатный путь может быть невозможен без отдельного
расследования, почему property-канал не поднимается — это исследовательская
задача, а не просто "добавить вызов".

Что нужно сделать (после/параллельно с расследованием mailbox):

- Разобраться, почему VideoCore mailbox не отвечает на этой сборке (channel 8
  property interface, база `0xfe00b880`, ARM_0_MAIL0 IRQ) — возможно, дело в
  порядке инициализации в elfloader/u-boot или в отсутствующей настройке
  GPU-стороны, которую делает штатная прошивка Raspberry Pi OS, но не делает
  наш загрузчик.
- Если mailbox поднять получится — реализовать минимальный property-tag
  клиент (запрос/ответ через shared buffer) и добавить вызовы
  `TAG_SET_CLOCK_RATE`/`TAG_SET_TURBO` в простое, аналогично тому, как
  `raspberrypi-cpufreq` дергает те же теги в Linux.
- Если mailbox принципиально недоступен на этой платформе/сборке —
  зафиксировать это как принятую деградацию (как уже сделано для RTC/NTP,
  см. `3.1`) и явно задокументировать, что ~5 Вт в простое — физическое
  ограничение текущей связки прошивки/загрузчика, а не то, что можно
  починить только в коде ОС.

## Фаза 5 — Остальная периферия BCM2711 (опционально)

Не задействовано в headless-архитектуре Psych Ward OS (единственный интерфейс — serial UART), каталогизировано на будущее:

- USB (host-контроллер) — для клавиатуры или внешних накопителей помимо SD
- GPIO (общее управление пинами) — если появится периферия помимо UART/сети/диска
- HDMI (видеовывод) — сейчас не нужен, вся ОС работает через serial
- Аудио (PWM/I2S) — не используется
- PCIe — потенциально для будущих ускорителей/сетевых карт
- Управление питанием — команда `reboot` (перезагрузка платы из shell)
- Мониторинг ресурсов — команды вроде `htop`/`df`/`free` (память, диск, нагрузка)

Монитор температуры (`temp` в shell) — сделано: единственный доступный без прошивки VideoCore термодатчик BCM2711 (AVS RO thermal, регистр статуса в блоке `avs-monitor@7d5d2000`) читается напрямую по MMIO тем же процессом, что и `timer_driver` (отдельный процесс не нужен — ни DMA, ни IRQ, ни инициализации). Подтверждено на живом железе.

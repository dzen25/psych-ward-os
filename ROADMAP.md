## Фаза 0 — Подготовка

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

Все платформо-зависимые адреса (UART/RTC/virtio-mmio, регистры PL031, GIC IRQ) вынесены в `src/h/platform.h`; убедились, что рефактор не сломал поведение на QEMU (boot/shell/net/disk/NTP). Заодно задокументирован quirk `timer_driver.cpp`: offset `0x10` использовался под именем «ICR» для PL031, хотя по датащиту это IMSC (реальный ICR — `0x1C`) — трогать не стали, поскольку весь этот код позже целиком ушёл при замене на ARM generic timer (Фаза 3.1).

## Фаза 1 — Hello World на живом железе

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

Собрана цепочка загрузки RPi4 (GPU firmware → device tree → `config.txt` → U-Boot → seL4-образ), установлена связь по UART через serial-консоль (GPIO 14/15, USB-UART, 3.3V), подтверждён ручной запуск на живой плате, автоматизирована загрузка через `boot.scr`. Всё проверено на тестовой hello-world сборке, отдельно от кода `psych-ward-os`.

Файлы цепочки лежат в [`load_chain_test/`](load_chain_test) (финальные образы — в [`load_chain/`](load_chain)): `start4.elf`, `fixup4.dat`, `bcm2711-rpi-4-b.dtb`, `config.txt`, `u-boot.bin`, `sel4test-driver-image-arm-bcm2711`. Скрипт автозагрузки — `boot.cmd`, скомпилированный в `boot.scr` (`mkimage`), лежит в корне FAT32-раздела SD-карты.

<details>
<summary><b>Как устроена цепочка загрузки, шаг за шагом (клик, чтобы развернуть)</b></summary>

| # | Стадия | Файл | Источник |
|---|---|---|---|
| 1 | FSBL | — (в ROM платы) | не трогаем |
| 2 | GPU firmware | `start4.elf`, `fixup4.dat` | [raspberrypi/firmware/boot](https://github.com/raspberrypi/firmware/tree/master/boot) |
| 3 | Device tree | `bcm2711-rpi-4-b.dtb` (+ `overlays/*`) | тот же репозиторий |
| 4 | Конфиг | `config.txt` | пишем сами: `arm_64bit=1` + `kernel=u-boot.bin` |
| 5 | Bootloader | `u-boot.bin` | собираем сами |
| 6 | seL4-образ | `sel4test-driver-image-arm-bcm2711` | результат сборки sel4test |

1. **BootROM** — прошито в кристалл SoC на заводе, не на SD-карте. Читает конфигурацию из EEPROM платы, единственная задача — найти и запустить `start4.elf`. Дальше всё на GPU (VideoCore VI), ARM-ядра ещё в reset.
2. **`start4.elf` + `fixup4.dat`** — закрытая прошивка VideoCore VI. Поднимает и калибрует SDRAM (на этом этапе ARM-ядра ещё ничего не могут), читает `config.txt` и device tree с той же SD-карты. `start4.elf` — вариант под BCM2711/Pi4, `fixup4.dat` — согласованная с ним таблица разметки памяти между GPU и ARM; версии всегда брать из одного релиза, не смешивать.
3. **`config.txt`** — парсит GPU firmware (ARM его не видит). Два значимых параметра: `arm_64bit=1` (поднять ядра сразу в AArch64) и `kernel=u-boot.bin` (что считать «ядром» и передать на выполнение).
4. **`bcm2711-rpi-4-b.dtb`** — машиночитаемое описание железа платы. GPU firmware грузит его в память и передаёт указатель ARM-ядрам через регистр x0. `overlays/*` — опциональные фрагменты под конкретную HAT-периферию, для базового boot не нужны.
5. **GPU firmware выпускает ARM-ядра из reset**, передаёт управление по адресу `kernel=` (обычно физический `0x80000`) с указателем на dtb в x0 — протокол загрузчика Linux-стиля, U-Boot тоже так собран.
6. **`u-boot.bin`** — реально первое, что исполняется на ARM. seL4-образ нельзя указать напрямую в `kernel=` (GPU firmware понимает только zImage/Image-подобные загрузчики) — U-Boot даёт консоль и команды `fatload`/`go`, чтобы положить seL4-образ по адресу `0x10000000` и прыгнуть туда.
7. **`sel4test-driver-image-arm-bcm2711`** (после Фазы 3 — готовый `psych-ward-os`) — seL4-ядро + root task, один плоский бинарник. U-Boot: `fatload mmc 0 0x10000000 <образ>` → `go 0x10000000`.

Команды сборки U-Boot, тестовой прошивки и автозагрузочного `boot.scr` — в [INSTRUCTIONS.md](INSTRUCTIONS.md).

</details>

</details>

## Фаза 3 — Порт дерева `psych-ward-os`

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

Создана ветка `RPi4`, дерево пересобрано с `-DPLATFORM=rpi4 -DRPI4_MEMORY=...` без правок `easy-settings.cmake`/`init-build.sh` (платформа нигде не захардкожена).

### 3.1 — ARM generic timer вместо PL031

Battery-backed RTC (PL031) на стоковой плате физически нет. Аптайм переведён на прямое чтение `CNTVCT_EL0`/`CNTFRQ_EL0` из EL0 (без трапа в ядро — `gen_config.yaml` этой сборки разрешает `EXPORT_VCNT_USER`). Wall-clock время решили брать только из NTP (I2C RTC-модуля на плате нет); без сети при старте offset остаётся 0 — принятая деградация, не баг. Подтверждено на живом железе (`time`/`uptime`/`sleep`).

### 3.2 — GENET вместо virtio-net

`net_driver.cpp` полностью портирован на GENET v5 (BCM2711 Ethernet MAC, RGMII PHY) — DMA-кольца TX/RX, MDIO, автосогласование скорости с реальным чтением результата (не хардкод), по образцу проверенного U-Boot-драйвера этой же платы. Поверх аппаратного слоя (ARP/IPv4/UDP/DNS/NTP-логика, которая переиспользовалась как есть) добавлен полноценный DHCP-клиент — получение IP/шлюза/маски/DNS вместо захардкоженных QEMU-адресов (`10.0.2.15`/`10.0.2.2`), обработка входящих ARP-запросов на собственный адрес (без неё соседи по сети со временем теряли нас из своего ARP-кэша и переставали быть в состоянии достучаться), прямой резолв MAC соседей по своей подсети вместо всегда-через-шлюз, честная разборка DNS-ответов (сервер не обязан сжимать имена, а не только по указателю), и правильная работа с некэшируемой DMA-памятью (кэш-когерентность между CPU и GENET). Подтверждено на живом железе: DHCP, ARP, ping до локальных и внешних хостов (вывод в формате обычного unix `ping`, со статистикой в конце), резолвинг доменов через DNS, NTP-синхронизация. Аппаратная граница вынесена в отдельный интерфейс (`net_hw_init/send/poll_rx/rx_done`), чтобы будущий Wi-Fi-бэкенд (Фаза 4) мог подключиться на то же место — заготовка в `wifi_driver.cpp`.

### 3.3 — EMMC/SD вместо virtio-blk

`blk_driver.cpp` портирован на реальный EMMC2 (Arasan SDHCI) — инициализация, чтение/запись блоков; FAT32-логика поверх переиспользована как есть. По пути найден и обойдён MBR на реальной SD-карте (раздел начинается не с нулевого сектора, в отличие от тестовых QEMU-образов) и восстановление `CONTROL0` после software reset (SRST_HC сбрасывает биты питания шины, недокументированная особенность контроллера). Подтверждено на живом железе: `ls`/`cat`/`touch`/`echo`/`mkdir`, несколько циклов перезагрузки подряд.

### 3.4 — UART / GIC

Только смена адресов в `platform.h`, логика не менялась — RPi4 использует GICv2 и PL011-совместимый UART0, те же, что и на QEMU. Boot readiness протокол (`SYS_DRIVER_READY`/`SYS_WAIT_ALL_DRIVERS_READY`) подтверждён со всеми живыми драйверами (timer/EMMC/GENET).

</details>

## Фаза 4 — Wi-Fi (BCM43455)

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

Wi-Fi на RPi4 обслуживается отдельным SDIO-хостом (`mmc@7e300000`), поверх которого живёт проприетарный протокол Broadcom (аналог `brcmfmac` в Linux — backplane enumeration, прошивка/NVRAM/CLM, sdpcm/BCDC IOCTL). Реализовано и подтверждено на живом железе: SDIO host bring-up, заливка прошивки/NVRAM/CLM-блоба, control-plane IOCTL-канал, PBKDF2-хендшейк и подключение к точке доступа по SSID/WPA2-PSK, скан точек доступа. Поверх control-plane реализован полноценный data-plane: `wifi_driver.cpp` и `net_driver.cpp` обмениваются кадрами через SHM TX/RX-мейлбокс, так что DHCP/ARP/ping/DNS/NTP работают через Wi-Fi так же, как через GENET, включая **полноценный dual-stack** — оба интерфейса одновременно активны, каждый со своим независимым IP/DHCP/ARP-кэшем.

Ключевые моменты:
- MAC-адрес чипа используется РЕАЛЬНЫЙ (`cur_etheraddr`), не выдуманный, как у GENET (там нет способа прочитать заводской MAC) — точки доступа могут молча дропать кадры с адресом, который не проходит anti-spoofing.
- Этот конкретный Wi-Fi SDIO-блок не поддерживает ни card-level in-band IRQ, ни ADMA2 (оба подтверждённо не работают на живом железе, сверено с `sdhci-iproc.c`) — в отличие от GENET/EMMC2, data-path остаётся на busy-poll + PIO.
- `wifi scan -f <2|5>` (фильтр по диапазону) не всегда достоверен — прошивка не всегда честно ограничивает список каналов в PASSIVE-режиме сканирования. Рекомендуется использовать `wifi scan` **без `-f`**.

**Актуальные команды:**
- `wifi start/stop/restart [-l]` — жизненный цикл процесса `wifi_driver`.
- `wifi scan [-t <сек>]` — скан точек доступа (без `-f`, см. выше).
- `wifi connect <ssid> [пароль] [-l] [&&save]` — подключение; `&&save` сохраняет пароль сети для будущих подключений без пароля - только `wifi connect <ssid> [-l]`.
- `wifi clean [all]` - стирает текущий пароль [all - стирает все пароли], `wifiprobe` — диагностика.
- `ping/send/sendto/recv/ntp [-W] ...` — без флага команда сама выбирает интерфейс (Ethernet, если у него есть IP; иначе Wi-Fi, если есть у него; иначе явная ошибка без сети); `-W` — принудительно через Wi-Fi.
- `netstat` — статус сразу обоих интерфейсов (GENET и Wi-Fi), без флагов.

</details>

## Фаза 5 — Безопасность: изоляция SHM по capability (least-privilege)

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

До этой фазы была одна каноническая физическая SHM-область — `SYS_SHM_GET` отдавала любому процессу (включая запущенные через `exec`) полный RW-доступ ко всей разделяемой памяти без проверки роли вызывающего; границы между «чужими» данными были только соглашением об офсетах, ничем не защищённым на уровне seL4 (пароль Wi-Fi лежал открытым текстом, независимые подсистемы уже реально пересекались по офсетам). Полностью закрыта (5.1-5.4), подтверждено на живом железе.

Ключевые моменты:
- `SYS_SHM_GET` решает по ролевой таблице (`is_driver` → битовая маска страниц), что получает каждый тип процесса; `exec`-процессы получают ноль страниц (fail closed), доступ к VFS — через узкий root-прокси (`SYS_PROXY_READ_FILE`/`SYS_PROXY_WRITE_FILE`, данные прямо в регистрах IPC, без SHM-capability).
- Права внутри разрешённых страниц сокращены до read-only там, где роль не пишет (`seL4_CNode_Mint`): `uart_driver` на VFS, `net_driver`/`shell` на Wi-Fi link-state, `net_driver` на GENET RX, `wifi_driver` на control-plane. На ARM нет write-only страниц — только RW→RO.
- Единая Wi-Fi-страница разбита на 3 (control-plane/link-state/TX-RX-мейлбокс) — 8 SHM-страниц вместо 6; пароль Wi-Fi зануляется самим `shell` сразу после подключения.
- Попутно найдены и исправлены два бага: `blk_driver` file-staging буфер пересекался с GENET RX-кольцом (вынесен на отдельную страницу); пустая маска страниц у `SYS_SHM_GET` возвращала ненулевой `vaddr` вместо 0 (контракт API был сломан).
- `NET_CMD_PING` переведён с SHM-мейлбокса на отложенный IPC-ответ (`SaveCaller`/`Send`/`Delete`, `shell` блокируется на `seL4_Call`) — потребовало отдельного ARP-таймаута (раньше маскировался таймаутом на стороне шелла). Остальные net-команды осознанно оставлены на SHM-мейлбоксе (DMA/TX-RX реально нужна разделяемая запись с обеих сторон).

</details>

## Фаза 6 — Многоядерность (SMP)

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

Ядро загружает все 4 ARM-ядра платы (spin-table, подтверждено логом `Core 1/2/3 is up`), `wifi_driver` реально перенесён на второе ядро. Подтверждено на живом железе (полный регресс + 8 циклов `wifi restart` с файловыми командами внахлёст на bring-up прошивки — `ps`/`netstat` без искажений).

Ключевые моменты:
- Флаги сборки — `-DSMP=ON -DNUM_NODES=4` (`easy-settings.cmake`, генерик sel4test-механизм, не специфично для rpi4).
- Все аппаратные прерывания по умолчанию остаются на ядре 0 (GIC таргетит на загрузочное ядро при старте) — перенос конкретного IRQ на другое ядро возможен (`seL4_IRQControl_GetTriggerCore`), но не сделан: не нужен для первого использования второго ядра.
- `wifi_driver` — единственный процесс, перенесённый на ядро 1 (`seL4_TCB_SetAffinity`, keyed на `is_driver`, переживает `wifi restart` без доп. состояния): его SDIO data-plane и так busy-poll/PIO (Фаза 4), корректность не зависит от ядра 0.
- Три independent non-atomic busy-spin лока на общей VFS-прокси SHM (`vfs_lock`/`net_vfs_lock`/`wifi_vfs_lock`, shell/net_driver/wifi_driver) заменены ОДНИМ мьютексом на seL4-нотификации (`seL4_Wait`/`seL4_Signal`, binary semaphore) — обычный hardware-atomic (LDXR/STXR) на этой SHM не годится: она Device-память ради когерентности с GENET DMA, а exclusive-monitor на Device-памяти уже роняло весь kernel на живом железе.

### Фаза 6.1 — Динамическое распределение по ядрам + `top`

Root умеет в рантайме переставлять уже запущенный процесс на другое ядро (`taskset <pid> <ядро>`), сам разгружать самое занятое ядро (`balance`) и показывать реальную нагрузку по ядрам и процессам (`top` — компактная таблица по ядрам, `top -l` — подробная построчная). Подтверждено на живом железе, включая перенос сетевых/блочных драйверов между ядрами без потери функциональности.

Ключевые моменты:
- `timer_driver` и root **не переносятся**, навсегда на ядре 0 — `timer_driver` держит ARM generic timer через PPI 30, который в GIC привязан к конкретному ядру (не multicore-aware `seL4_IRQControl_Get`); перенос уронил бы таймер и с ним все heartbeat'ы при первом же перевзведении на новом ядре. `SYS_SET_AFFINITY`/`balance` явно защищают оба процесса от переноса.
- Нагрузка — штатный `seL4_BenchmarkGetThreadUtilisation` (`-DKernelBenchmarks=track_utilisation`), не самодельная эвристика. Учёт utilisation в ядре seL4 — per-ядро, а не глобальный, поэтому для ядер 1-3 root просит представителя (любой активный uart/blk/net/wifi процесс на этом ядре) самому включить/выключить учёт и отдать честный total/idle своего ядра (`collect_load_snapshot()`, общая для `top` и `balance`). Ядро без ни одного из четырёх драйверов (только шелл/exec) честно показывает "нет данных" — это предел механизма, не баг.
- `balance` — по команде, но цель переноса выбирает алгоритм: находит самое занятое ядро с ≥2 резидентами, оставляет там "тяжёлый" (максимальный %CPU) процесс в одиночестве, остальных раскидывает по наименее загруженным ядрам. root/timer_driver под той же защитой, что у `taskset`.
- `top` — разовый снимок (не live, как в Linux) — консоль общая с фоновыми логами драйверов, ANSI-перерисовка не окупает сложность.

**Найдено и исправлено, подтверждено на живом железе** (полная история
диагностики — в git; текущие открытые находки — `issuse.txt`):
`<<seL4(CPU 0) [checkInterrupt/59]: Spurious interrupt!>>` ("checkInterrupt/59"
— это НЕ номер IRQ, а строка в `kernel/src/api/syscall.c`, где стоит этот
`userError`) сыпалось на КАЖДОЙ команде, трогающей диск — воспроизводилось
даже БЕЗ единого вызова `balance`/`taskset` за сессию, значит первоначальная
гипотеза про миграцию ядра/GIC-таргет была неверна. Настоящая причина:
`blk_driver.cpp` после монтирования диска включал реальный GIC-сигнал
(`EMMC_IRPT_EN_OFFSET = EMMC_INT_ALL_EN`) для CMD_DONE/DATA_DONE/READ_RDY/
WRITE_RDY, хотя единственная функция, которая эти события реально ждёт
(`emmc_wait_irpt_bit()`), уже давно переведена на чистый busy-yield по
`CNTVCT_EL0` и сама, опережающе, Ack'ает IRQHandler через полинг — настоящее
(чуть отложенное) аппаратное прерывание для того же события доходило до CPU
УЖЕ ПОСЛЕ этого опережающего Ack'а, GIC был уже деактивирован, и
`checkInterrupt()` рапортовал "Spurious interrupt!". Исправлено: IRPT_EN для
этих битов теперь всегда 0 (статус по-прежнему читается полингом, просто без
дублирующего аппаратного прерывания).

Заодно в эту же фазу (найдено при тестировании `taskset`/`kill`/`balance`
на живом железе, не связано с ядрами напрямую, но тем же циклом
диагностики): бейджи клавиатурной/таймерной IRQ-нотификации (`uart_driver`/
`timer_driver`) совпадали с диапазоном PID — после watchdog-респавна
`uart_driver` освободившийся PID=1 рано или поздно доставался обычному
клиенту и вешал консоль навсегда; исправлено именованными вне-PID-диапазона
константами (`UART_KBD_IRQ_BADGE`/`TIMER_IRQ_BADGE`, common.h), тем же
принципом, что уже применён у blk/net/wifi. И течь capability-слотов в
`SYS_EXIT` (main.cpp) — обычный (не аварийный) выход процесса чистил только
3 капы вместо всего `cap_tracker`, копилось на каждой команде, вело к
`Out of CSlots`; исправлено — тот же полный цикл очистки, что уже был в
`generic_recover_process`/`SYS_THREAD_EXIT`. Оба подтверждены на железе.

**В планах:** live-обновление `top`. (Авто-`balance` при загрузке одного
ядра уже закрыт побочно в Фазе 9.B; две ранее найденные, не регрессирующие
WIFI-находки — мейлбокс на Device-памяти без явной документации порядка,
WIFI_LINK_STATE без арбитража записи — расследованы и закрыты
документацией, см. Фазу 11.)

## Фаза 7 — DVFS/cpufreq + энергодомены VideoCore (✅ закрыто)

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

Старый вывод "VideoCore mailbox физически не отвечает" оказался неверным —
причина была в двух багах кода: спутаны mail0/mail1 status-регистры
(проверка "есть ли место для записи" читала не тот регистр) и property-буфер
аллоцировался из RAM выше 1ГиБ, недостижимой для ARM→VC bus-адресации. Оба
исправлены (сверкой с реальным драйвером U-Boot), канал живой.

Реализовано и подтверждено на живом железе:
- `cpufreq` — заявленная/измеренная (`GET_CLOCK_RATE_MEASURED`, честная
  проверка железа, не эхо запроса)/мин/макс частота ARM, `cpufreq set
  min|max`. Пользователь поднял потолок 1500→1800МГц (`arm_freq=1800` в
  `config.txt` — плата официально поддерживает, Rev 1.4, раскодировано из
  ревизии в логе U-Boot). 600↔1800 реально переключаются.
- Авто-губернатор (`SYS_CPUFREQ_GOVERNOR_TICK`, тикает вместе с фоновым
  `balancer` раз в ~5с): первая версия на
  `seL4_BenchmarkGetThreadUtilisation` не сработала — busy-poll драйверы
  (blk/wifi/GENET) и heartbeat-будильник никогда не давали системе
  выглядеть простаивающей. Переделано на честный признак:
  `SYS_MARK_SHELL_ACTIVITY` — shell сообщает root момент каждой новой
  команды, `SYS_BALANCE` сравнивает с текущим временем (нет ввода ≥8с →
  min, иначе → max). Подтверждено: сам уходит в 600МГц без ручных команд.
  Инерция до ~5с (интервал тика `balancer`) — реакция не мгновенная,
  ожидаемо для poll-based дизайна.
- `peripherals` + автоматическое отключение при старте 16 неиспользуемых
  мультимедиа-энергодоменов VideoCore (`SET_DOMAIN_STATE`, найдено через
  реальный Linux-драйвер `raspberrypi-power.c` — гораздо шире старого
  `SET_POWER_STATE`, который реализован лишь для пары legacy-устройств):
  HDMI, VEC, JPEG, H264, V3D, ISP, обе камеры (UNICAM0/1),
  CSI2/CCP2RX/CPI, DSI0/1, TRANSPOSER, CCP2TX, CDP. Подтверждено 16/16
  выключено. Сознательно не тронуты: ARM (наши же ядра), I2C0-2/
  VIDEO_SCALER/VPU1 (не используются, но неочевидная семантика), USB
  (отдельный, более рискованный домен).

**Итог по энергопотреблению**: суммарный эффект от DVFS + отключения
доменов на практике скромный, заметно меньше, чем рассчитывали. Основной
бюджет ~5 Вт простоя держат вещи, которые мы не трогаем: SDRAM-рефреш,
базовый тактовый домен самого VideoCore (который выполняет прошивку и наш
же mailbox-канал — его закрыть невозможно в принципе), Ethernet-PHY,
USB-контроллер. Зафиксировано как практический потолок для этой платы без
более глубокого вмешательства — не баг, дальше не копаем.

Мелкая незакрытая находка, не критично: `TRANSPOSER` в `peripherals`
иногда показывает `ON` после отключения при старте (остальные 15/16
держатся стабильно `off`) — вероятно, что-то в дисплейном пути включает
его обратно как побочный эффект; не мешает и не расследовано отдельно.

</details>

## Фаза 9 — Сервисная архитектура: `/bin`, `/sbin`, init.conf, регистрозависимая ФС

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

Вынести команды шелла и внешние сервисы в отдельные `.elf` под `/bin`/`/sbin`,
добавить init.conf-автозапуск сервисов, сузить привилегии админ-syscall'ов,
сделать ФС регистрозависимой. Сделано по частям (A→D), каждая проверена на
живом железе отдельно.

### 9.A — `/bin`, `/sbin`: команды шелла как отдельные `.elf` (✅ подтверждено на живом железе)

`ps`/`kill`/`taskset`/`top`/`balance`/`ls`/`cat`/`touch`/`rm`/`mv`/`mkdir`
вынесены из `shell.cpp` в `/sbin/*.elf` — тонкие обёртки вокруг уже
существующих syscall'ов, вся серверная логика (таблица процессов, TCB-капы)
остаётся внутри root. Шелл при нераспознанной команде пробует
`exec /sbin/<команда>.elf`.

- Новая доверенная категория `is_driver==253` — RW SHM только на VFS-
  страницу + капа общего VFS-мьютекса (обычный `exec` остаётся fail-closed,
  Фаза 5). Общий клиентский IPC-бойлерплейт — в новом `h/sys_client.h`.
- Пайпинг (`ps | grep`) для `/sbin`-команд как левой стороны пайпа —
  изначально было известным, принятым ограничением (`exec`-нутые процессы
  не писали в `pipe_fd`), реализовано отдельно, см. Фазу 11.
- На железе найдены и исправлены 3 бага подряд: (1) cwd передавался через
  фиксированный офсет VFS SHM-страницы, но офсет считался от неверного
  размера страницы (16384 вместо реальных 4096) — фолт на каждой команде;
  (2) даже после фикса офсета — `load_elf_from_disk()` читает `.elf` через
  ТУ ЖЕ физическую SHM-страницу, куда шелл только что записал cwd,
  затирая его раньше, чем ребёнок успевал прочитать — cwd переехал с SHM
  на выделенный слот boot-IPC (`EXEC_CWD_MSG_SLOT`, common.h); (3) обычный
  `return 0;` из `main()` в этом рантайме не работает (нет crt-эпилога) —
  добавлен обязательный `sys_exit()` перед каждым `return`.

### 9.B — `/etc/init.conf` + автозапуск сервисов, `balancer.elf` (✅ подтверждено на живом железе)

Root читает `/etc/init.conf` (`<имя> <путь> <приоритет> <ядро>`, `-1` =
не переставлять) при старте и поднимает перечисленные `/service/*.elf` —
без пересборки ядра. Ошибка в одной строке — лог и переход к следующей, не
паника. Заодно закрыт пункт "авто-`balance`" из планов Фазы 6.1: обычный
автозапускаемый сервис `balancer.elf` (спит N мс → `SYS_BALANCE` →
повторить, интервал — из `/conf/balancer_conf/balancer.conf`) вместо
отдельного механизма в root.

- Сервисы получают ту же категорию `is_driver==253`, что и `/sbin` (9.A).
- `wifi_driver` вынесен из CPIO-образа на диск (`/service/wifi.elf`,
  грузится по требованию через `SYS_START_WIFI`, включая watchdog-респавн)
  — не через `init.conf` (несёт свой богатый набор capability, генерик-
  парсер сервисов это не должен понимать).
- Wi-Fi прошивка/NVRAM/CLM/пароли переехали `/wifi/...` → `/conf/wifi_conf/...`.
- На железе найден и исправлен полный отказ загрузки: 4 разных места
  (`SYS_EXEC`/`SYS_START_WIFI`/watchdog-респавн wifi/`start_init_services`)
  читали `.elf` в СВОИ отдельные статические буферы по 1МБ каждый — лишние
  +3МБ BSS сдвинули carve-up untyped-памяти под CNode-слоты и роняли самый
  первый спавн. Исправлено: один общий `g_elf_load_buffer` на все 4 места
  (root однопоточный, параллельного доступа не бывает).

### 9.C — least-privilege проверка вызывающего для admin-syscall'ов (✅ подтверждено на живом железе)

Исходная задумка ("узкий API для балансировщика, чтобы не давать ему TCB-
прав") уже была закрыта Фазой 9.B побочно — `balancer.elf` и так простой
клиент без единой TCB-капы. При проверке этого допущения нашлась реальная
дыра: `SYS_KILL`/`SYS_SET_AFFINITY`/`SYS_BALANCE` вообще не проверяли,
кто вызывает — любой процесс с `root_ep` (есть у ВСЕХ, включая
недоверенный `exec`) мог убить любой PID, перенести процесс на любое ядро
или запустить ребалансировку. Заодно нашлась эскалация привилегий в
`SYS_EXEC`: категория `is_driver=253` выдавалась по одному совпадению
префикса `/sbin/...`, без проверки самого вызывающего.

Исправлено: `is_admin_caller(pid)` (true только для shell/253) — проверка
добавлена в начало всех трёх admin-syscall'ов и в присвоение `is_driver=253`
при `SYS_EXEC` (легитимные пути не затронуты). Сравнение префикса `/sbin/`
заодно стало регистрозависимым.

### 9.D — регистрозависимая ФС (⛔ вытеснено Фазой 10)

Фикс `fat32.cpp` (сравнение LFN-имён `my_strcasecmp`→`my_strcmp` в поиске
и удалении) был сделан и работал для новых имён, но на живом железе
выяснилось: каталоги/файлы, созданные ВНЕШНИМИ инструментами (Finder/
`diskutil` при копировании на карту) для имён, укладывающихся в 8.3 без
потерь (`bin`, `config.txt`...), вообще не получают LFN-запись — источник
не в сравнении при поиске, а в том, что таким именам просто не пишут LFN
на этапе создания, а создаёт их не наш код. Переформатирование не
помогало. Решение — полный уход на exFAT, где короткого имени не
существует вообще, см. Фазу 10.

</details>

## Фаза 10 — Уход с FAT32/8.3 на exFAT

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

Весь класс багов вокруг DOS 8.3/LFN (регистронезависимость, отсутствие LFN
у файлов/каталогов, созданных внешними инструментами) структурно
невозможен в exFAT — там одно длинное имя на файл, короткого алиаса нет
вообще. Этапы A-C (монтирование+чтение, запись, переключение) подтверждены
на живом железе. План (байтовые раскладки структур exFAT, сверенные с
эталонными реализациями — Linux kernel exfat-driver, exfatprogs) —
`/home/nikita/.claude/plans/optimized-honking-sunbeam.md`.

На первом прогоне Этапа B нашёлся баг "дублирования" записи при повторном
`echo>` в тот же файл — при диагностике выяснилось, что причина не в
exFAT-коде: `shell.cpp` не обрезал завершающие пробелы при разборе
аргументов команд, что раньше маскировалось space-padding коротких имён
FAT32/8.3 и впервые стало видно на exFAT, где короткого имени нет вообще.
Исправлено (обрезка пробелов в `shell.cpp`; `exfat_normalize_path()`
дополнительно обрезает пробелы в каждом компоненте пути, как
defense-in-depth на уровне ФС).

Заодно добавлена общая защита от дублей для всех команд, создающих файлы
(`touch`/`mkdir`/`echo>`/...): вместо тихого no-op или перезаписи —
явное предупреждение в консоль, если имя уже существует
(`exfat_create_file`/`exfat_mkdir` получили выходной параметр
`out_existed`, `blk_driver.cpp` различает статус 0 (создан) / 1 (уже
существует) / -1 (ошибка), `touch.cpp`/`mkdir.cpp` печатают "уже
существует — ничего не делаю").

Ключевые моменты:
- ROM-загрузчик RPi4/U-Boot читают загрузочные файлы своим FAT12/16/32-
  ридером прошивки, exFAT не понимают — аппаратное требование, не
  меняется. Карта теперь ДВЕ MBR-партиции: 1 — FAT32 (только загрузочные
  файлы, наш код не монтирует и не трогает никогда), 2 — exFAT
  (`/bin/sbin/etc/conf/service/root`, монтирует `blk_driver`). Партиция 2
  ищется по MBR-типу `0x07` (`find_exfat_partition()`, неоднозначен с
  NTFS) — `exfat_init()` жёстко сверяет реальную сигнатуру.
- Новый `src/exfat.cpp`/`h/exfat.h`, API зеркалирует `fat32.h` — замена в
  `blk_driver.cpp` механическая (`fat32.cpp`/`.h` не удалены, просто больше
  не подключены). exFAT не хранит `"."`/`".."` — путь резолвится текстовой
  нормализацией (`exfat_normalize_path`) ДО обхода диска. Каталоги бывают
  смежным экстентом (`NoFatChain=1`, свои) ИЛИ настоящей FAT-цепочкой
  (корень; чужеродные, например от Finder) — `DirExtentCache` переносит
  это между `resolve_parent()`→`find_in_dir()`/`format_dir_listing()`.
- Имена — ASCII-фолд без чтения on-disk Upcase Table (для ASCII-диапазона
  стандартная дефолтная таблица идентична нашему `a-z→A-Z`).
- Запись (Этап B): битовый аллокатор поверх Allocation Bitmap, только
  смежные пробеги (свои экстенты в FAT не участвуют вообще); свой
  `NameHash`/`SetChecksum` при записи набора directory entries; каталоги —
  1 кластер без роста; повторный `echo>` в тот же файл переписывает набор
  записей на месте (не ищет новую позицию, иначе плодил бы дыры).
- Найдено и исправлено на первом прогоне: переполнение стека blk_driver
  (глубокий вызывной путь Этапа B, каждое звено с `DirCursor`/
  `sector_buf[512]` на кадре — перевалил за старые 4КБ) — стек увеличен до
  16КБ на процесс, для всех процессов (`spawn_process`, main.cpp).

Деплой: карта — 2 партиции (см. `issuse.txt` за командами `diskutil`),
флашится флагом `-b` (код драйвера — часть образа ядра на партиции BOOT).

</details>

## Фаза 11 — Надёжность: конкурентные sleep, stale capability, respawn, pipe, парсер конфига

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

Серия независимых находок из `issuse.txt`, закрытых в одну сессию, с общей
темой: устранение хрупких мест в IPC/процессной модели, вскрытых
длительным реальным использованием (нагрузочные тесты Wi-Fi, `kill`/
respawn, конфиги).

- **Конкурентные `sleep`**: `timer_driver` держал только ОДИН отложенный
  sleep одновременно (единственный аппаратный ARM generic timer
  мультиплексировался через software timer wheel, но слот был один) —
  второй одновременный `sleep()` от другого процесса молча отклонялся
  (-1), а вызывающий код это не проверял. На практике это давало
  случайные "зависания" `ping`/`ntp` через Wi-Fi, требовавшие
  `kill net_driver` — на самом деле не сетевой баг, а `wait_for_net_mailbox()`
  считала прошедшее время числом вызовов `sleep(100)`, что ломалось, как
  только чей-то ещё `sleep` конкурентно отклонялся. Исправлено на двух
  уровнях: (1) `wait_for_net_mailbox()` меряет реальное время через
  `sys_get_uptime()`; (2) по предложению пользователя — `timer_driver`
  расширен с 1 до 8 конкурентных слотов (`MAX_PENDING_SLEEPS=8`,
  `rearm_timer()` перевзводит один аппаратный компаратор на ближайший из
  всех активных дедлайнов). Подтверждено на живом железе.
- **Stale capability после `kill`**: убийство процесса с зависшим
  отложенным IPC-ответом (например ждущего `sleep`/UART-чтение) оставляло
  у `timer_driver`/`uart_driver` капу на уже уничтоженный TCB — следующее
  обращение в этот слот сыпало безобидное, но пугающее
  `Attempted to invoke a null cap` в консоль ядра. Исправлено новым
  syscall'ом `SYS_CANCEL_PENDING_FOR_PID` — `generic_recover_process()`
  явно просит каждого драйвера с отложенным ответом отменить и почистить
  капу для убитого PID перед продолжением recovery (осознанный выбор
  полного фикса, а не документирования как безобидного). Подтверждено на
  живом железе.
- **Watchdog не мог респавнить произвольные процессы**: логика респавна в
  `generic_recover_process()` была захардкожена под конкретные роли
  (`if (meta.is_driver == 5) { load "/service/wifi.elf" }`) — процессы,
  запущенные с диска через `SYS_EXEC`/`init.conf`, при краше вообще не
  восстанавливались. Исправлено: новое поле `path` в
  `ProcessControlBlock` запоминает исходный диск-путь при каждом спавне
  (`SYS_EXEC`, `start_init_services()`, `SYS_START_WIFI`), респавн стал
  общим — `load_elf_from_disk(blk_ep, meta.path, ...)`. Подтверждено на
  живом железе.
- **Pipe для `/sbin`-команд** (`ps | grep`, ранее — известное ограничение
  Фазы 9.A): `sys_write(fd, ...)` в `sys_client.h` уже был общим по FD —
  единственное недостающее звено было в том, что `spawn_process()`
  жёстко минтил `local_console_ep` в FD 1 вместо капы пайпа. Добавлен
  параметр `stdout_pipe_id`, `shell.cpp` передаёт id пайпа через
  exec-payload при пайпинге. Осознанно ограничено только `/sbin`-командой
  слева от `|` (справа — только `grep`, как и раньше). Подтверждено на
  живом железе.
- **Парсер `/conf/balancer_conf/balancer.conf`**: раньше требовал, чтобы
  число было самым первым, без единой пустой строки/комментария перед
  ним; теперь пропускает пустые строки и строки-комментарии (`#`/`;`)
  перед числом и явно предупреждает в консоль (вместо тихого fallback на
  умолчание), если конфиг всё равно не начинается с числа или число
  равно 0. Подтверждено на живом железе.
- Заодно закрыты документацией (без изменения поведения) две находки
  Фазы 6.1 про Wi-Fi SHM: TX/RX-мейлбокс без явного порядка доступа —
  безопасен благодаря ARM Device-memory ordering (задокументировано в
  `platform.h`); `WIFI_SHM_LINK_STATE_OFFSET` без арбитража записи —
  безопасен, потому что `SYS_STOP_WIFI` всегда сначала suspend'ит TCB
  `wifi_driver`, прежде чем root сам туда пишет.

</details>

## Фаза 12 — Защита от подмены бинарников (Ed25519-подписи) (✅)

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

Все файлы, которые `load_elf_from_disk()` (`main.cpp`) читает с диска для
исполнения/использования — `/sbin/*.elf`, `/service/*.elf`,
`/etc/init.conf` — теперь должны нести действительную Ed25519-подпись,
иначе rootserver отказывается их использовать (fail-closed, без исключений
для "старых неподписанных" файлов). Единая точка проверки прямо в
`load_elf_from_disk()` автоматически покрывает все 5 мест, которые её
вызывают (`SYS_EXEC`, `init.conf`, watchdog-респавн, автозапуск сервисов,
`/service/wifi.elf`) — без единого изменения в вызывающем коде: отказ
(`-1`) уже трактуется всеми ими как обычная ошибка чтения диска.

**Модель доверия**: защищает партицию 2 (exFAT
— `/sbin`, `/service`, `/etc/init.conf`) от подмены кем/чем угодно без
приватного ключа — включая физический доступ к SD-карте и гипотетические
баги/эксплойты самой ОС. **Не защищает** загрузочную FAT32-партицию и сам
образ ядра — тот грузит U-Boot вообще без проверки подписи. Никакого
пароля/разрешения внутри самой ОС нет и не нужно — ОС только проверяет
подписи, никогда не создаёт и не принимает новые ключи в рантайме; доверие
устанавливается полностью офлайн, на сборочной машине.

Тот же концепт для загрузочной FAT32-партиции (образ ядра + boot-команда) —
теперь Фаза 13, отдельным механизмом (RSA/FIT, проверяется самим U-Boot,
`tools/sign_elf`/Monocypher/`OS_PUBLIC_KEY` отсюда не переиспользуются).

Ключевые моменты:
- **Ed25519 через Monocypher** (`tools/monocypher/`, вендорено как исходники
  в общую сборку rootserver'а — без code-gen шага и отдельной библиотечной
  цели, в отличие от nanopb), не RSA/mbedtls: на два порядка меньше
  ключи/подписи, без опасных схем паддинга (PKCS#1), быстрее на слабом ARM.
  Проверка/подпись сразу над сырыми байтами файла — отдельный шаг
  "посчитать SHA-256, потом подписать хэш" (как в исходной концепции от
  другого агента) чистому Ed25519 не нужен, он хэширует внутри сам.
- **Формат подписи** — 68-байтовый трейлер (4-байтовый magic `"PWSG"` +
  64-байтовая подпись) в конце файла, а не отдельная ELF-секция:
  `load_elf_from_disk()` и так уже возвращает реальный размер файла с диска
  (не вычисленный из ELF-заголовков), достаточно просто обрезать трейлер
  при успешной проверке — ни парсинг ELF, ни вызывающий код не меняются.
  Работает одинаково для `.elf` и текстового `init.conf`.
- **Ключи**: публичный (`OS_PUBLIC_KEY[32]` в `main.cpp`) — не секрет, зашит
  в прошивку. Приватный — `.signing-key` в корне репозитория (в `.gitignore`,
  никогда не коммитится и не попадает на SD-карту), сгенерирован один раз
  `tools/sign_elf/sign_elf genkey`.
- **`tools/sign_elf/`** — маленькая автономная офлайн-утилита (собирается
  хостовым `gcc`, без ARM cross-toolchain, не встроена в основной CMake —
  никогда не попадает на плату). `sign_elf genkey <файл>` печатает публичный
  ключ C-массивом для вставки в `main.cpp`; `sign_elf sign <ключ> <in> <out>`
  дописывает трейлер.
- **`build_and_sign.sh`** (корень репозитория) — весь пайплайн одной
  командой: пересобирает `sign_elf` при необходимости, проверяет/предлагает
  сгенерировать ключ, гоняет `ninja`, раскладывает и подписывает всё в
  `load_chain/` по списку папок (не хардкод конкретных имён файлов — новая
  `/sbin`-команда подхватывается сама).
- Найден и исправлен баг при внедрении: генератор ключа писал на диск
  seed ПОСЛЕ вызова `crypto_ed25519_key_pair()`, а та сама защитно затирает
  свой параметр `seed[]` изнутри — на диск улетали нули вместо настоящего
  ключа. Поправлено (запись до вызова), ключ перевыпущен.
- **Подтверждено на живом железе**: `init.conf` грузится, `balancer`
  автозапускается, команды с диска (`ps`/`ls`) работают.

</details>

## Фаза 13 — Secure boot загрузочного образа (FIT/RSA-подпись, U-Boot) (✅)

<details>
<summary><b>Подробности (клик, чтобы развернуть)</b></summary>

Продолжение Фазы 12 на загрузочную FAT32-партицию: образ ядра seL4 и сама
boot-команда теперь требуют RSA-подписи, проверяемой **самим U-Boot**
(`CONFIG_FIT_SIGNATURE`), а не rootserver'ом — когда rootserver получает
управление, доверять ему для этой проверки уже поздно.

**Область защиты**: образ ядра (обёрнут в FIT) + boot-команда
(`CONFIG_BOOTCOMMAND`, `boot.scr` упразднён). **Не защищено и не может
быть**: `start4.elf`/`fixup4.dat`/`config.txt`/FAT32-копия
`bcm2711-rpi-4-b.dtb`/сам `u-boot.bin` до своего запуска — грузятся
GPU-прошивкой RPi4 раньше, чем U-Boot существует. Настоящая защита этого
уровня — только OTP secure boot платы (прожиг fuse-битов, необратимо,
риск окирпичить) — осознанно отклонено как непропорциональный риск.

**Дизайн: merge узла `/signature` в DTB прошивки, а не замена.**
`CONFIG_OF_BOARD` остался на дефолте (включён) — DTB прошивки как и всегда
единственный источник аппаратного описания. Первый вариант (замена DTB
через `--disable OF_BOARD`) на реальном железе трижды ломался — сначала
нумерация MMC (свой DTB не задаёт алиасы `mmc0`/`mmc1`), затем режим SD
(нехватка `mmc-ddr-3_3v`), и в итоге упёрлись в настоящий, невылечиваемый
точечными патчами баг: `mmc read` рапортует успех, но физически не пишет в
память (сравнение узлов DTB показало полную идентичность — вплоть до DMA
это не свойство дерева). Архитектура сменена: небольшой патч
`board_fdt_blob_setup()` (`board/raspberrypi/rpi/rpi.c`, хранится как
`tools/boot_fit/rpi_merge_signature.patch`, применяется
`setup_uboot_secure_boot.sh` через `git apply`, идемпотентно) копирует
узел `/signature/<key>` из СВОЕГО (OF_SEPARATE) DTB — куда `mkimage -K`
по-прежнему вписывает ключ — в DTB прошивки ПЕРЕД использованием, дженерик
по свойствам (`fdt_for_each_property_offset`, без хардкода RSA-полей).

Место под слияние — **фиксированный физический адрес (`0x08000000`)**, не
`static`-буфер и не `malloc()`: первая версия патча со статическим буфером
компилировалась и проходила все офлайн-проверки, но на живом железе плата
тихо перезагружалась каждые ~5 сек без единой ошибки. Причина (нашли в
`arch/arm/lib/crt0_64.S`): U-Boot зачищает свою `.bss` СРАЗУ ПОСЛЕ переноса
себя на новый адрес (relocation), прямо перед `board_init_r` — а
`board_fdt_blob_setup()` вызывается раньше, из `board_init_f`. Общий урок:
любой код, пишущий в `.bss` до релокации и читающий после — гарантированно
теряет данные в U-Boot; нужен адрес вне собственного образа (тот же класс
памяти, что уже занимает `fw_dtb_pointer`, `reloc_fdt()` копирует его в
безопасное место сам).

Ключевые моменты:
- **RSA-2048 + FIT (`mkimage`)**, не Ed25519 из Фазы 12 — должен уметь сам
  U-Boot (`CONFIG_FIT_SIGNATURE`).
- **`CONFIG_LEGACY_IMAGE_FORMAT` отключён** — иначе проверка была бы
  опциональной, а не fail-closed.
- **Ключ**: `.fit-signing-key/` в корне (в `.gitignore`, каталог), RSA-2048
  через `openssl genpkey`/`req`. Встраивается в `u-boot.dtb`/`u-boot.bin`
  через `mkimage -K ... -r` (`-r` = `required`, обязательная проверка).
- **`tools/boot_fit/boot.its.template`** — один `kernel-1`, `arch=arm64`,
  `os=u-boot`, `type=kernel`, `load=entry=0x10000000` (тот же адрес, что
  раньше в `boot.scr`).
- **`build_and_sign.sh`**, шаг `[6/6]` — подписывает актуальный образ в
  `load_chain/boot.itb`. Пересборка `u-boot.bin` — отдельно,
  `setup_uboot_secure_boot.sh`.
- **Проверено локально** хостовым `tools/fit_check_sign`: валидный образ,
  испорченные данные (`Bad Data Hash`), чужой ключ
  (`Failed to verify required signature`) — все три сценария ведут себя
  правильно. Сам merge в DTB прошивки локально не проверить —
  `board_fdt_blob_setup()` выполняется только на реальной загрузке.

**Путь до рабочей boot-команды (5 попыток на железе, 2026-08-03)**:
подпись и merge заработали по-настоящему на 4-й попытке
(`Verifying Hash Integrity ... sha256,rsa2048:dev+ OK`, историческая
нумерация MMC вернулась), но следом — три отдельных, не связанных с
DTB/ключами бага уровня FIT/boot-команды: (1) `boot.itb` грузился в тот же
адрес (`0x10000000`), куда `bootm` потом копирует распакованное ядро —
`bootm` пытался скопировать ядро поверх ещё не разобранного контейнера
(`ERROR: new format image overwritten`) — поправлено, контейнер теперь
грузится в `0x20000000`, ядро по-прежнему в `0x10000000`; (2) `os = "linux"`
(взято по инерции из другого хелпера seL4, легаси-uImage) заставлял `bootm`
искать заголовок настоящего Linux ARM64 Image, которого у сырого elfloader
нет (`Bad Linux ARM64 Image magic!`) — поправлено на `os = "u-boot"`
(`do_bootm_standalone()`, тот же голый вызов точки входа, что раньше делал
`go`); (3) без сохранённого `uboot.env` переменная `autostart` не задана —
`do_bootm_standalone()` в этом случае вообще не вызывает точку входа, тихий
мгновенный возврат трактуется `boot_selected_os()` как фатальный
(`Resetting the board...`). Первая попытка чинить — `type = "standalone"`
— оказалась неверной: этот тип не проходит валидацию `kernel=`-образа в
`boot/image-fit.c` (`No ... Kernel Image`), значит и не нужна была —
достаточно `setenv autostart yes` в `CONFIG_BOOTCOMMAND`, `type` вернули на
`"kernel"`. Заодно всплыла (и осталась полезной) неточность в самопроверке
`setup_uboot_secure_boot.sh`: `fit_check_sign` может вернуть ненулевой код
не из-за самой подписи, а из-за отдельного шага-симуляции полной загрузки —
самопроверка теперь ищет в выводе `Verified OK, loading images`, не
полагается на код возврата целиком.

  Ещё не сделан отдельный **негативный тест**:
  испорченный/неправильно подписанный `boot.itb` должен дать чистый отказ
  U-Boot (проверено локально через `fit_check_sign`, три сценария — не
  хватает подтверждения на живом железе).

</details>

--- wifi_driver.cpp (SDIO + CYW43xx + WPA2) ---

4. Нет обнаружения разрыва связи после успешного connect — состояние
    "подключено" остаётся навсегда
    wifi_driver.cpp:3336-3343 (обработка deauth/disassoc) против
    единственных писателей WIFI_SHM_LINK_STATE_OFFSET (3739/3742/3585).
    BRCMF_E_DEAUTH/_IND и BRCMF_E_DISASSOC_IND разбираются только внутри
    wifi_wait_for_join_result() (единственная точка вызова, 3506, внутри
    wifi_connect()). После успешного WIFI_CMD_CONNECT канал событий больше
    никогда не читается — heartbeat (3663-3686) опрашивает только канал
    данных.
    Как воспроизвести: успешно выполнить `wifi connect <ssid> <pass>`,
    затем выключить/унести точку доступа — `wifi status`/`ping -W`/`ntp`
    продолжат считать линк поднятым (падение видно только на уровне
    таймаутов транспорта) до ручного `wifi connect`/`wifi restart`.

5. [ПОПЫТКА ФИКСА 2026-08-10 ОТКАЧЕНА после hw-теста — сломала `wifi
    connect` (100% таймаут join), см. разбор ниже] Кадры канала данных
    теряются/задерживаются во время блокирующих wifi connect/wifi scan
    wifi_driver.cpp:1657-1662 (комментарий, признающий пробел), 3663-3686
    (RX/TX только по heartbeat), 3506 (wifi_connect блокирует до 15с),
    3757-3758 (wifi scan по умолчанию 30с, настраивается -t). Пока
    синхронно выполняется обработчик WIFI_CMD_CONNECT/WIFI_CMD_SCAN, ни
    путь дренажа F2, ни TX-mailbox не выполняются.
    Как воспроизвести (сам баг): `ping -W <host>`, затем сразу `wifi scan
    -t 30` — любой входящий кадр/ответ во время 30-секундного скана
    никогда не вычитывается из аппаратного FIFO в RX-mailbox и теряется,
    ping не увидит ответ даже если точка доступа его отправила.
    ПОСТМОРТЕМ неудачной попытки фикса: добавили дренаж data-канала
    (sdpcm_try_read_one_data_frame(), тот же код что в heartbeat-
    обработчике) внутрь poll-циклов wifi_wait_for_join_result()/
    wifi_wait_and_dump_any_events(). На hw это сломало `wifi connect`
    НАСМЕРТЬ (5/5 попыток — "таймаут ожидания событий join"), `wifi
    scan` внешне продолжил работать (нашёл 7 сетей) — вероятно повезло
    с таймингом, а не по-настоящему безопасно. Причина:
    sdpcm_try_read_one_data_frame() делает sdio_f2_read() и БЕЗУСЛОВНО
    забирает следующий кадр из ОБЩЕЙ F2-очереди — data/event/control там
    физически перемешаны, канал кадра различим только ПОСЛЕ чтения (по
    тегу внутри самого кадра, см. channel = ...&0x0F). Если выдернутый
    кадр оказывается EVENT (например SET_SSID/PSK_SUP, которых как раз
    ждёт join, или ESCAN_RESULT для скана), функция видит "не наш канал"
    и просто отбрасывает его (return false) — но кадр уже физически снят
    с шины и потерян для того, кто его реально ждал. Фикс отсюда полностью
    откачен (git diff — все следы wifi_drain_data_channel_once() и
    g_wifi_net_rx_ntfn убраны). Правильное решение потребовало бы
    настоящего диспетчера кадров (прочитанный кадр не по нашему каналу —
    буферизировать/передать дальше, а не молча дропать) — заметно больше
    по объёму и риску, чем однострочный вызов дренажа; отложено.

6. [ЕСТЬ, НО НЕ ВЫРАЖЕНО В ШЕЛЛЕ] Потоковая запись доступна тестам и
   команде `cp`,
   которая сама выбирает режим по размеру. Отдельного оператора или
   команды, открывающей поток прикладному коду напрямую, нет. Заводить
   имеет смысл, только если появится потребность: `cp` уже покрывает
   основной случай "скопировать файл известного размера". ПРИЧИНА ЗАВОДИТЬ

   так что отдельный режим больше не даёт выигрыша в скорости — только
   в удобстве, если понадобится писать поток из прикладного кода.

7. [ОТКРЫТО] Горячее подключение нестабильно.
   Уже исправлено в последней сборке, но, видимо, не всё:
     * handle_port_status_change перечислял устройство заново по ЛЮБОМУ
       Port Status Change при CCS=1 (второй Address Device с кодом 4 и
       сброс порта 1 = встроенного хаба) — теперь только по CSC и только
       если на порту ещё нет устройства; общий код с секундным опросом;
     * ежетиковый опрос хабов крал события асинхронного сброса порта
       ("SET_PORT_FEATURE(RESET) не удался", "порт не сообщил о
       завершении сброса") — TRB AsyncCtrl теперь слушатели в кэше;
     * сбрасываются все биты изменения порта хаба, порт, выключенный
       хабом (C_ENABLE), переподключается; Interrupt-EP хаба
       восстанавливается после ошибки.
   Подозрения по коду (НЕ проверены на железе), по убыванию вероятности:
     а) ПОТЕРЯ ВТОРОГО ПОДКЛЮЧЕНИЯ ЗА ХАБОМ. poll_hub_interrupts сначала
        безусловно снимает C_PORT_CONNECTION, а потом зовёт
        hub_conn_async_start(), которая при занятой стейт-машине
        (g_hub_conn_state != IDLE — она одна на всю систему) молча
        выходит. Бит уже снят, хаб больше не напомнит — устройство не
        перечислится до следующего физического переподключения. Типичный
        случай: два устройства почти одновременно (комбо-хаб SS+HS,
        быстрое переткнутие).
     б) быстрое переподключение в КОРНЕВОЙ порт: при CSC=1 и уже
        существующем устройстве на порту обработчик теперь ничего не
        делает (сделано осторожно, чтобы не повторить двойную
        энумерацию) — старый слот останется висеть. Linux в этом случае
        снимает старое устройство и перечисляет новое;
     в) при таймауте AsyncCtrl его TRB остаются в кольце EP0 хаба
        неисполненными, следующий запрос встаёт за ними;
     г) переподключение порта, выключенного хабом, откладывается, пока
        занята стейт-машина подключения, и держится только на том, что
        хаб повторит событие.

8. [ОТКРЫТО] Нет Ctrl+C и прочих управляющих сочетаний.
   Клавиатура отдаёт Ctrl+буква как управляющий код (Ctrl+C = 0x03),
   ровно как minicom, но в системе НЕКОМУ его обработать: ни uart_driver,
   ни шелл, ни root не знают о прерывании выполняющейся команды (поиск по
   0x03/SIGINT/Ctrl по всему коду пуст) — то же самое и при наборе из
   minicom, это пробел ОС, а не клавиатуры. Нужно: механизм прерывания
   (uart_driver видит 0x03 в любом источнике ввода -> сообщает root ->
   root останавливает процесс переднего плана) и решение, кто считается
   "передним планом".
   Там же, но уже про клавиатуру: не передаются Delete, Home/End,
   PgUp/PgDn, Insert, F1-F12 (шелл разбирает только трёхбайтные
   ESC [ A-D), Alt игнорируется, цифровой блок не учитывает NumLock,
   индикаторы CapsLock/NumLock не горят (нужен control-OUT с данными —
   SET_REPORT, такого помощника в драйвере нет).

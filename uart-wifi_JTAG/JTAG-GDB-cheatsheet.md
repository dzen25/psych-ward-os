# Памятка: как пользоваться JTAG-отладчиком

Подробности архитектуры (мост, найденные баги, почему всё устроено именно так) — в `Rp2040-jtag-uart-guide.md`, §8. Здесь — только «что нажимать» и «что делать, если что-то пошло не так».

---

## Запуск

VSCode → панель **Run and Debug** (`Ctrl+Shift+D`) → выбрать в списке `JTAG: RPi4 kernel.elf через OpenOCD/DirtyJTAG (cpu0)` → **F5**.

Само по себе поднимется: мост (Python) → OpenOCD → GDB подключится к порту 3333 (ядро cpu0). Занимает ~20-30 секунд — мост медленный (одно USB-обращение на каждый JTAG-бит), это нормально, не зависание.

---

## ⚠️ Главное правило, которое легко забыть

**Перед тем как жать красный квадрат Stop — сначала Continue (▶).**

Кнопка Stop в VSCode просто отключает GDB. Она **не** говорит процессору «продолжай работу». Если остановить сессию, пока ядро стоит на паузе (halted), оно **так и останется физически замороженным** — UART, шелл, всё зависнет намертво, даже когда никакого отладчика уже не подключено. Это не баг моста, а особенность halt/debug-request на ARM: состояние остановки защёлкивается в самом ядре и держится, пока кто-то явно не пришлёт resume.

**Если это всё же случилось** (UART молчит после закрытия отладки) — восстановить без перезагрузки платы:
```bash
telnet localhost 4444
# или: nc localhost 4444
> targets          # посмотреть, какое ядро halted
> resume
> targets           # проверить, что теперь running
```
(порт 4444 — telnet-консоль OpenOCD, поднимается автоматически вместе с ним; если сам OpenOCD уже не запущен — сначала стартани задачи `JTAG: bridge...` и `JTAG: OpenOCD...` из палитры команд (`Ctrl+Shift+P` → `Tasks: Run Task`), не через F5, чтобы не тянуть за собой полное GDB-подключение).

## Пауза (⏸) во время работы

Кнопка Pause в панели отладки шлёт прерывание через тот же медленный мост — может отвечать так же ~10-20 секунд, не сразу. Если кажется, что не реагирует — подожди. Если правда не реагирует, надёжная альтернатива:
```bash
nc localhost 4444
> halt
```
Это гарантированно останавливает ядро напрямую через Tcl-консоль OpenOCD, независимо от того, что делает GDB/VSCode.

## Точки останова

Клик слева от номера строки в исходнике (`.c`/`.cpp`/`.S`) — до или после Continue, без разницы. Символы ядра (`kernel.elf`) и юзерленда (`sel4test-driver` — там `wifi_driver.cpp`, `blk_driver.cpp`, `main.cpp`) загружены в одну сессию, брейкпоинт можно ставить в обоих местах.

Типичный сценарий «поставить точку и запустить что-то по UART»:
1. Поставить breakpoint (например на `wifi_dongle_bringup` или `wifi_sdio_probe` в `wifi_driver.cpp`).
2. Continue.
3. Из отдельного терминала (minicom/serial) ввести команду в шелл, которая доходит до этой функции.
4. GDB сам остановится на брейкпоинте.

Проверить, что символы юзерленда подгрузились:
```
break wifi_dongle_bringup
```
`Breakpoint 1 at 0x...` — всё ок. `Function not defined` — символы не загрузились, `add-symbol-file` в `launch.json` не сработал, разбираться отдельно.

## Что вводить в Debug Console (когда цель на паузе)

**Что делает процессор:**
```
bt                      # стек вызовов
info registers          # регистры общего назначения
disassemble             # ассемблер вокруг текущего PC
```

**Сырые дампы памяти:**
```
p/x g_wifi_base                          # адрес MMIO-региона SDIO/EMMC2
x/16xw $g_wifi_base                      # 16 слов (64 байта) с этого адреса
p EMMC_CONTROL1_OFFSET                   # константа-смещение (если видна в символах)
x/1xw $g_wifi_base+EMMC_CONTROL1_OFFSET  # конкретный регистр контроллера
```
Общий синтаксис: `x/<количество><формат><размер> <адрес>` — `x` = hex, `d` = decimal, `w` = word(4B), `g` = giant(8B), `b` = byte.

## Если совсем всё встало (мост/OpenOCD не отвечают)

```bash
pkill -f dirtyjtag_bitbang_bridge.py
pkill -f openocd
```
и заново через F5. USB-устройство от этого не пострадает — мост просто переоткрывает соединение при следующем старте.

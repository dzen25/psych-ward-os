# Беспроводной UART мост на ESP32-C3 (QT Py)

Цель: заменить проводной USB-UART адаптер беспроводным мостом, чтобы снимать serial-консоль RPi4 по WiFi, без кабеля к Mac. JTAG (FT232H) при этом остаётся отдельным проводным каналом — см. `jtag-uart-rpi4-guide.md`.

Плата: **Adafruit QT Py ESP32-C3**, доступные пины: `0-10, 20, 21, 5V, 3.3V, GND`.

Способ прошибки и работы с Serial Monitor можно посмотреть на ютубе или почитать где нибуть.

---

## 1. Схема

```
   RPi4 GPIO14 (TXD) ──── GPIO20 (RX0) ESP32-C3
   RPi4 GPIO15 (RXD) ──── GPIO21 (TX0) ESP32-C3
   RPi4 GND          ──── GND         ESP32-C3
```

GPIO20/21 на C3 — аппаратный UART0, совпадает с объектом `HardwareSerial UartBridge(1)` в коде ниже (не путать с `Serial` — тот привязан к USB-CDC для диагностики через Serial Monitor, физически на UART-пины не выведен).

LED-индикаторы (опционально, показывают трафик TX/RX):
```
GPIO2 → резистор 220-330Ω → анод LED_TX → катод → GND
GPIO1 → резистор 220-330Ω → анод LED_RX → катод → GND
```

Питание: USB (отдельный кабель/повербанк) или 3.3V-пин от RPi4 (не 5V напрямую от Pi без проверки — 5V пин C3 идёт до собственного стабилизатора платы).

Рекомендация поставить 2 конденсатора:

Электролитический (или танталовый) конденсатор, 100-470 мкФ, на 6.3V или выше — ставится максимально близко к пинам 3.3V/GND платы. Он отвечает за "медленную" ёмкостную буферизацию — сглаживает просадки на масштабе миллисекунд, компенсируя бросок тока при TX-импульсе WiFi.

Керамический конденсатор, 100 нФ (0.1 мкФ), параллельно первому, максимально близко к самим пинам питания чипа — отвечает за высокочастотный шум, который электролит физически не успевает фильтровать из-за своей более высокой паразитной индуктивности.

## 2. Настройки WiFi-сети (обязательно, иначе не подключится)

ESP32-C3 поддерживает только **2.4GHz**, режимы b/g/n. Требуемые настройки роутера:

| Параметр | Значение | Почему |
|---|---|---|
| Шифрование | **WPA2-PSK (CCMP)**, не mixed WPA2/WPA3 | SAE/WPA3 нестабильно поддерживается arduino-esp32 |
| 802.11w (PMF) | **Disabled (0)** | Обязательный PMF ломает handshake на C3 |
| Разрешить 802.11b | **включено** | Без этого — `AUTH_EXPIRE`, кадр авторизации не проходит на некоторых AP |
| Ширина канала | **20 MHz** | 40MHz на 2.4GHz даёт нестабильность на простых embedded-чипах |
| Канал | фиксированный (не auto), напр. 1/6/11 | Предсказуемость |
| Код страны | указать явно (не `00`) | Влияет на тайминги/regulatory domain |
| SSID | отдельный от 5GHz, без band steering на одном имени | Иначе AP может пытаться увести клиента на недоступный C3 диапазон |

Для OpenWrt (uci):
```bash
uci set wireless.wifinet1.encryption='psk2'
uci set wireless.wifinet1.ieee80211w='0'
uci set wireless.radio0.legacy_rates='1'
uci set wireless.radio0.country='RU'
uci commit wireless
wifi reload
```

## 3. КРИТИЧНЫЙ питфол — TX Power

На полной мощности передачи (дефолт ~20dBm) конкретно эта плата **не проходила WPA handshake** — hostapd на роутере не видел вообще ни одного кадра от платы (полная тишина в `logread -f`), при том что сеть прекрасно принималась (`RSSI -50..-60`). Симптом стабильно воспроизводился на нескольких версиях кода, независимо от настроек роутера.

**Диагноз (по совокупности, не 100% доказано):** проблема в передающей части/питании при пиковом токе TX на полной мощности — возможно, локальная просадка при броске тока в момент передачи, не обязательно фиксируется как `ESP_RST_BROWNOUT` в `esp_reset_reason()`.

**Решение — обязательно снизить мощность передачи:**
```cpp
WiFi.setTxPower(WIFI_POWER_11dBm);
```
Поставить сразу после `WiFi.mode(WIFI_STA)`, до `WiFi.begin()`. С этой строкой подключение стабильно работает.

Если нужна большая дальность — можно постепенно поднимать (13dBm, 15dBm...) и проверять, на каком уровне снова начнутся обрывы — так находится баланс для конкретного экземпляра платы.

## 5. Подключение с Mac или Linux

Узнать IP платы: через Serial Monitor при старте (`Connected! IP address: ...`) либо через DHCP-таблицу роутера.

Установить socat и minicom:

```bash
brew install socat minicom # Mac

apt install socat minicom # Linux
```

**Самый простой способ:**

```bash
# дать права на исполнение файла uart.sh который находится в текущей папке:

chmod +x uart.sh

# и запустить его:
./uart.sh
```

**Простой способ:**
```bash
nc <ip-адрес-платы> 23
```

**Через picocom (если сборка поддерживает telnet://):**
```bash
picocom --baud 115200 telnet://<ip-адрес-платы>:23
```

**Через minicom (нужен socat-мост, т.к. minicom не работает с сырым TCP напрямую):**
```bash
brew install socat
socat pty,link=/tmp/esp32c3,raw,echo=0 tcp:<ip-адрес-платы>:23 &
minicom -D /tmp/esp32c3 -b 115200
```
Выход из minicom: `Ctrl-A`, затем `X` (с подтверждением) или `Q` (без).

## 6. Диагностика проблем подключения (порядок действий)

Если WiFi не подключается — методичный порядок, который реально сработал:

1. **Пустой Serial Monitor** → проверить, что `Serial` не спутан с `HardwareSerial(1)` — на платах с native USB (QT Py C3) `Serial` = USB CDC, физически на GPIO20/21 не выведен.
2. **`WiFi FAILED to connect`, (можно загнать этот пункт в нейронку чтоб она добавила логирования) статус 6 (`WL_DISCONNECTED`)** → добавить `WiFiEvent`-обработчик, смотреть `Disconnect reason`:
   - `reason 2` = `PREV_AUTH_NOT_VALID` — обычно смежная проблема (PMF/шифрование/TX power), не буквально "неверный пароль".
   - `reason 201` = `NO_AP_FOUND` — несмотря на то что сеть видна в скане; может быть шум от `scanNetworks()`, вызвать `WiFi.scanDelete()` после скана.
   - `AUTH_EXPIRE` на стороне роутера (`logread`) — обычно 802.11b rates выключены на AP, включить.
3. **Проверить пароль независимо** — подключить телефон к той же сети тем же паролем. Если телефон не подключается — пароль/панель ни при чём, значит дело в самом пароле.
4. **Смотреть `logread -f` на роутере параллельно с попыткой подключения C3** — если там вообще ничего не появляется (полная тишина, ни одного кадра) — проблема на стороне передачи/питания C3, а не в конфигурации роутера. См. раздел 3 (TX Power).
5. **Band steering** — если SSID общий для 2.4/5GHz, роутер может игнорировать 2.4GHz авторизацию от способных на 5GHz устройств. Для C3 это не проблема "выбора диапазона" (физически не видит 5GHz), а именно поведение AP — держать отдельный SSID для 2.4GHz.

## 7. Нагрев платы — норма

Заметный нагрев при активной WiFi-сессии — ожидаемое поведение (радио + LDO-регулятор питания рассеивают тепло, плата маленькая — площадь рассеивания малая). Порог тревоги: если невозможно держать палец на плате дольше секунды — проверить кабель/блок питания на предмет качества, полноценные ли 5V. `setTxPower(WIFI_POWER_11dBm)` заодно и снижает нагрев по сравнению с дефолтными ~20dBm. Рекомендуется применить радиатор для долгой работы.

## 8. Как работают индикаторы.

Подключенные светодиоды rx и tx после включения ESP32-C3 моргают 5 раз сигнализируя о успешной загрузке платы. Затем загораются оба на 1 секунду после чего моргают еще раз сигнализируя о успешном подключении к WiFi. Далее работают как сигнализаторы ввода-вывода UART.
